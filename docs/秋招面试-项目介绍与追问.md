## 二、项目口头介绍稿（2-3 分钟）

好的，我简单介绍一下这个项目。

这个项目是一个 **AI 长篇小说自动生成系统**。核心目标是把"写一本小说"从传统的人工构思、人工写作，变成输入一句话创意，系统自动完成世界观构建、人物设计、大纲规划，再到逐章正文的完整生成。整个链路端到端自动化，作者只需要做审核和把关。

**先说整体架构，我把它分成四层：**

第一层是模型层。我们适配了 DeepSeek 和 Gemini 两个大模型，通过统一的 Provider 抽象封装，一个模型不可用或质量不达标时能自动切换，保证长任务稳定运行。

第二层是 Agent 核心层，也是我重点设计的通用任务图引擎。我把一次生成任务拆成一个个有依赖关系的任务节点，每个节点自带角色、技能、工具、验收标准和 Token 预算；执行器按依赖关系逐个执行，产物以强类型契约在节点间传递——比如世界观产物、角色集、大纲契约、章节草稿，全部用 Pydantic v2 定义，保证上下游数据不错位。

第三层是小说领域层。我在通用核心上做了领域插件，编排小说创作的专业流程，也就是简历里写的四阶段流水线：故事架构师做世界观、角色设计师做人物、大纲规划师做剧情、章节执行者逐章写作。这里有个关键设计是 **Plan-and-Execute**：不是死流程，而是先让模型根据需求自己生成执行计划，系统映射成任务图；如果模型生成的计划校验失败，就自动降级到预置的确定性流程。既保留灵活性，又保证极端情况不跑偏。

第四层是数据与交互层。产物、运行状态、记忆全部持久化到 SQLite，支持多项目隔离；交互上有 Gradio WebUI 控制台和 WebAPI 两种方式。

**再说两个我比较有信心的亮点：**

一个是**跨章节记忆系统**。长篇小说生成最大的痛点是"写着写着忘了前面的设定"，人物崩坏、伏笔不回收。我在每个章节节点挂了记忆抽取工具，章节生成完自动把新出现的人物、设定、情节线索抽取存库；每个章节生成前做连续性审计，检查角色一致性、时间线、伏笔是否与前文冲突，冲突就走质量评审不通过、触发定向修订重写。这套机制保证了长周期连载不崩人设。

另一个是**可靠性工程**。小说生成是长任务，中途容易遇到 API 超时、服务中断。我做了一个完整运行状态机，支持暂停、恢复、取消；每一步产物都提交持久化，中断后能断点续跑、不丢进度；还有 Token 预算控制防止单节点失控，以及工具调用审计台账，模型每次调了什么工具、结果如何都有记录，方便回溯。

**使用上**，作者在 WebUI 里选项目、填一句需求描述、点开始就行。界面实时展示运行状态快照、章节产物和质量评审报告；哪章不满意可以单独重写，或回退到之前版本重新生成；也提供 WebAPI 和命令行脚本支持批量跑项目。

技术栈是 Python 3.11 + Gradio + Pydantic v2 + SQLite，模型走 OpenAI 兼容协议，配了 json-repair 做输出容错解析，并用 pytest 覆盖了核心图编排逻辑的测试。我主要负责整体架构设计和核心模块实现，从通用 Agent 核心到领域插件再到工程化交付是一套完整闭环。

## 三、面试官深挖追问（模拟 Q&A）

### 第一轮：架构与设计动机

**Q1：任务图为什么不用 LangGraph/AutoGen 等现成框架，要自己写？**

我的核心诉求不是"能跑通多智能体"，而是**可控性和可恢复性**：每个节点要有验收标准、Token 预算、产物契约、审计记录，节点失败要能单独重跑，这些在 LangGraph 里要改很多东西。而且核心只需要一个有向无环的依赖编排 + 状态持久化，自研任务图引擎（TaskGraph + NodeExecutor 抽象）只包含"节点定义 + 执行器 + 产物仓库"三个概念，后续扩展领域只是往图里插节点，成本很低，也不引入重依赖。

**Q2：节点有哪些属性？为什么这么设计？**

节点核心属性：`task_type`（任务类型）、`role`（角色，如故事架构师）、`skills`（声明式技能清单）、`tools`（工具白名单，如 `world.generate`、`chapter.draft`）、`acceptance`（验收条件，如 `continuity_ok`、`quality_accept`）、`budget_tokens`（Token 预算）、`output_contract`（产物契约类型）。

好处是**执行器完全通用，领域差异全部被数据化**：执行器只负责"拿工具、调模型、验契约、查验收、落库"，换领域就是换一组节点和工具，不需要改引擎。

### 第二轮：Plan-and-Execute 与降级

**Q3：模型生成的计划是什么格式？怎么保证它不乱来？**

计划是规划生成器调模型产出的一份**结构化执行计划**（ExecutionPlan），包含有序步骤列表，每步指定工具名和参数。生成后有两层把关：

1. **结构校验**：Pydantic 契约解析，格式不对直接判失败；
2. **语义校验**：步骤顺序合法性——必须先有世界观才有角色、必须有角色才能有大纲、章节号必须连续递增，非法顺序被拒绝。

**Q4：模型给不出合法计划怎么办？**

模型计划是"增强"而非"必须"。当计划缺失或校验失败，系统置 `degraded` 标记，**自动回退到预置的确定性流程模板**：按用户意图（只要世界观/只要角色/只要大纲/完整小说）直接构建对应任务图，如完整小说固定为"世界观→角色→大纲→N 章"。降级原因会被显式记录（plan_info），保证可观测。模型规划失效时任务依然能完整跑通。

**Q5：动态计划和固定模板的图有什么区别？**

动态计划可能只生成部分节点（如用户只想改两个角色，计划里就只有 `character.revise` 和对应章节节点）；固定模板是全量流程。动态计划会保留语义节点 ID（world/cast/outline/chapter_N），依赖边仍确定性构建，后续审计、恢复逻辑无需区分图的来源。

### 第三轮：记忆系统与质量闭环（重点）

**Q6：跨章节记忆系统具体怎么实现？**

分三步：

1. **抽取**：章节节点执行完正文后调用 `memory.extract`，抽取本章**新出现的角色、设定、势力、关键情节线索**为结构化记忆条目；
2. **存储**：记忆和角色档案、世界观一起持久化到 SQLite，并做**角色名归一化**（相似度匹配把"李明/李铭"这类偏差归一到已有档案，避免记忆碎片化）；
3. **使用**：下一章生成前，将相关记忆（前文摘要、角色档案、当前进度）注入章节生成上下文，让模型"带着记忆写下一章"。

**Q7：连续性审计怎么审？发现冲突怎么办？**

审计器（ContinuityAuditor）在章节草稿产出后执行 `continuity.audit`，检查人物是否 OOC、时间线是否错乱、伏笔是否矛盾、设定是否与世界观冲突。审计结论配合 `quality_accept` 验收条件决定章节是否通过。

**不通过时不会全局重写**，而是走**定向修订**：触发 `chapter.repair` / targeted-revision，只对冲突段落局部重写，旧版本保留为 revision——既省 Token，又避免"修一处坏一片"。

**Q8：质量评审的"评审员"怎么实现？每次都用大模型会不会很贵？**

评审员是一个**可切换的持有器**（reviewer holder）：流程早期用**离线接受器**（规则/契约级检查，零成本）；等角色设定产物生成后才切换为**真实的大模型评审员**。且质量评审工具与实际使用的评审员是同一实例，保证"审的就是写的那版"。评审节点有独立 Token 预算，只在章节级执行，不会失控。

### 第四轮：可靠性工程

**Q9：状态机有哪些状态？断点恢复怎么做到无缝续跑？**

生命周期：排队（queued）→ 运行中（running），期间可**暂停（paused）/取消（cancelled）**，异常走失败（failed），成功进完成态，并有独立恢复流程。

断点续跑的关键是**每步产物立即提交**：节点执行完，产物（草稿、审计结果、记忆条目、工具调用记录）在同一 SQLite 事务里落库，图状态同步持久化。重启后恢复器扫描运行事件流，从"最后一个已提交节点"之后继续执行，**已完成的节点绝不重复跑**，不重复消耗 Token。工具调用有独立审计台账（ledger），记录参数、结果、耗时，既是恢复依据也是排查依据。

**Q10：Token 预算超了怎么办？双模型切换策略？**

每个节点有 `budget_tokens`，执行器每次调用前检查剩余额度，超限即终止该节点并标记失败原因，防止单节点吃光整个任务预算。

模型切换不是"挂了就换"：Provider 层把失败分类——网络/超时等瞬时错误走指数退避重试；连续重试失败或配额类错误才触发**模型切换**（DeepSeek/Gemini 互为备份），切换记录到运行事件，可观测。

**Q11：用户中途想改需求（如"把女主改成反派"）怎么办？**

走 revision 体系：WebUI 发起**定向修订**——`character.revise` 只重建角色集节点，下游依赖章节被标记失效需重新生成；或对单章发起 REVISE 命令，构建单节点重写图强制重写。新版本作为新 revision 提交，**旧版本不覆盖**，可对比、可回退（Rebase 为显式确认操作，防呆设计上要求输入确认载荷）。核心原则：**任何修改都可追溯、可回退**。

### 第五轮：存储与工程化

**Q12：存储层怎么设计？多项目、并发怎么处理？**

数据分五类：项目资产（世界观/角色/大纲/章节）、运行事件流、记忆库、工具审计台账、版本 revisions，全部 SQLite 落盘，按项目隔离目录。写入统一走事务封装，保证"产物 + 状态 + 事件"原子提交。

并发：本地运行调度器让任务排队串行执行，避免 SQLite 写竞争；WebAPI（api_v1/v2）与 WebUI 共用同一套 service 层，多入口不会状态不一致。

**Q13：测试怎么写的？覆盖哪些关键逻辑？**

pytest 为主，重点覆盖**图编排正确性**：领域插件在不同意图下构建的节点集合、依赖边是否符合预期（世界观在角色前、章节号连续）、计划到图的映射、降级路径。这类纯逻辑与模型调用解耦（有 offline 假实现），CI 可跑，无需真实 API。

### 第六轮：开放性收尾

**Q14：项目最大的挑战是什么？**

最大的挑战是**"长任务的确定性"**：生成式模型天然不稳定，而长篇小说是几十个节点、长周期的流水线，任何一步的漂移都会连锁放大——角色崩了后面全崩。所有设计都围绕这一件事：

- Plan-and-Execute 把"怎么走"交给模型，但保留降级兜底；
- 契约校验把"数据对不对"变成硬约束；
- 连续性审计 + 定向修订把"写错了"控制在局部；
- 状态机 + 断点恢复把"挂了"变成可续跑。

"不确定的模型 + 确定性的工程护栏"，是这个项目收获最大的思维方式。

**Q15：给两周时间继续优化，最想做哪个方向？**

1. **成本优化**：每章生成链路中审计、评审的重复调用还有压缩空间——缓存已审计段落、按风险分层评审；
2. **评估体系**：目前 evaluate 有基础质量评估，缺一套与人工评分对齐的量化指标，有了它才能数据化调 Prompt 和流程参数。

## 四、架构选型口头介绍（Plan-and-Execute vs ReAct）（面试口语版）

> 面试官视角："为什么考虑用 Plan-and-Execute 架构，为什么不用 ReAct 或者其他 agent 架构？"——不含代码细节，只讲设计思路。

我选型的原则是：**架构没有优劣，只有匹配。先看任务特征，再选架构。**

这个任务的特征是：第一，创作流程是强领域先验——写小说必须先有世界观、再有角色、再有大纲、才能写章节，这个依赖关系**事先就知道，不需要探索**；第二，它是几十章的长任务，一次运行有几百次模型调用；第三，质量要逐章把关，而且中途失败必须能恢复。

而 ReAct 的核心是"边做边想"：模型思考一步、调用工具、看结果、再思考。它适合的是"每步都要看工具结果才能决定下一步"的**探索型任务**（搜索问答、查资料决策）。但小说创作恰恰相反——路径是已知的，不需要每步探索。用 ReAct 会带来三个问题：

1. **决策点爆炸**：ReAct 每章要走好几轮"思考-行动-观察"，三十章下来几百个决策点，每个都是漂移风险，任何一步坏输出都会带偏整个循环；而规划-执行把"路径"收敛成**一次**低温、强约束的规划决策，决策点从几百个降到几个；
2. **成本不可控**：ReAct 模型想循环几轮就几轮，调用次数不可预期；规划-执行是一次规划 + 每章固定次数的门控调用，还有节点级预算，成本可预测；
3. **可恢复性（最关键的）**：小说任务必须能断点续跑。ReAct 的状态藏在对话历史里，崩溃了从哪恢复说不清；而规划-执行里**计划本身是一份结构化、可落库、可审计的产物**——恢复就是"从最后一个已提交的节点继续"，失败能分类、能重试、能降级。"计划即数据"是整套可靠性设计的地基。

另外还有一点：我的审计、评审、验收全部挂在**固定的流程节点**上，保证每章走同一套门；ReAct 的路径自由恰恰让"门挂在哪"都说不清，质量没有可比基线。

其他架构我也对比过：纯推理的 CoT 没有工具执行；树状探索的 ToT 适合开放探索，对单线小说是成本浪费——它的分支能力我留给了版本体系（revision）；反思式的 Reflexion 有价值，我把它**降维吸收**成"评审不过就定向修订"的受控机制；多模型辩论成本太高，我用"独立裁判"（评审模型与写作模型分离）实现了轻量版。

最后要诚实说一点：**ReAct 不是没用**。我系统里章节节点内部其实就是"受控的 ReAct"——生成之后要抽记忆、审计、评审，审计和评审的结果会反馈到下一步决策（不通过就修复）。只不过这个循环被严格约束：工具集固定、次数固定、动作有权限。所以准确的架构描述是：**规划-执行决定路径，节点内受控循环处理局部反馈**——把自由留给需要反馈的地方，把确定性留给不需要自由的地方。

一句话总结：**路径是已知的就不该每步探索，质量要门控就不能路径自由，长任务要恢复就必须计划即数据——这三件事 ReAct 给不了，Plan-and-Execute 天然具备。**

## 五、架构选型技术深挖（追问细节）

### 5.1 选型依据：任务特征

| 任务特征 | 本项目情况 | 对架构的影响 |
|---|---|---|
| 流程可预测性 | 世界观→角色→大纲→章节，依赖关系是领域先验 | 路径不需要探索，P&E 一次规划即可 |
| 任务时长 | 几十章长流程，数百次模型调用 | 决策点必须收敛，成本必须可预测 |
| 决策点密度 | 路径决策很少，执行决策很多 | 路线决策收敛为一次低温规划，执行照单做 |
| 失败代价 | 中途失败恢复成本极高 | 必须"计划即数据"，显式可恢复 |
| 成本敏感 | 每多一次调用被几十章放大 | ReAct 的无界循环不可接受 |

### 5.2 为什么不用 ReAct（五个理由）

1. **决策漂移放大**：ReAct 每章 5-10 次"思考-行动-观察"，30 章 = 150-300 个路径决策点，每个都是漂移机会；P&E 把路径收敛成一次 T=0.3 的强约束规划（工具白名单 + JSON Schema + 规则），决策点从几百降到几个；
2. **成本差一个数量级且不可预期**：ReAct 循环次数由模型决定；P&E 一次规划 + 每章固定门控调用，节点级 Token 预算（budget_tokens），成本可预测可控；
3. **可恢复性**：ReAct 状态隐式存在于对话历史，无法断点恢复；P&E 计划是显式产物（结构化/可校验/可审计/可持久化），恢复 = 从最后已提交节点继续，失败分类（parse/schema/validation/transport）精确、可重试、可降级确定性模板；
4. **质量门控挂点**：审计/评审/验收挂在固定节点上（continuity_ok、quality_accept），确定性管线保证每章走同一套门，质量有可比基线；ReAct 路径自由导致门控无处可挂；
5. **失败可定位**：P&E 每个节点独立失败、独立重试、独立审计，问题精确到节点；ReAct 循环里坏输出难以定位。

### 5.3 与其他架构的对比

| 架构 | 核心思想 | 为什么不选 / 如何吸收 |
|---|---|---|
| CoT | 纯推理链 | 无工具、无产物落库，创作需要工具化执行与持久化 |
| ReAct | 推理-行动交替循环 | 决策点过多、成本不可控、状态隐式难恢复 |
| ToT | 树状多分支探索 | 适合开放探索（游戏叙事）；分支能力由 revision 体系承接（并行分支版本） |
| Reflexion | 反思改进循环 | 降维吸收为"质量不达标→定向修订"受控机制（max_repairs=2），不做全局无界循环 |
| 多智能体辩论 | 多模型互评 | 成本 ×N；用"独立裁判"（writer/judge 不同模型）实现轻量版 |
| LangGraph 式图编排 | 显式图执行 | 与任务图同源；P&E 是在图之上加规划层，二者互补不冲突 |

### 5.4 混合真相：节点内受控 ReAct

项目不是纯 P&E：章节节点执行器依次调用生成→抽记忆→审计→评审，**工具结果反馈到决策**（审计硬冲突→暂停；评审不过→触发修复）——即"观察→再行动"。但循环被三重约束：

- 工具集固定（节点 `tools` 白名单 + 网关权限矩阵）；
- 次数固定（max_repairs=2，修复预算封顶）；
- 动作受审批（chapter.draft/repair/memory.extract 需 COORDINATOR 审批）。

准确架构描述：**P&E 决定路径 + 节点内受控 ReAct 处理局部反馈**。若未来任务需要实时外部信息决策（查知识库、查玩家行为），可放开节点内循环或引入 ToT 分支探索——架构跟着任务特征走。

### 5.5 一句话总结

**ReAct 是"边做边想"的灵活派，适合探索型任务；小说创作是"先想后做"的执行型任务——路径是领域先验、质量要门控、长流程要恢复。P&E 把不确定性收敛到一次可校验的规划，把确定性留给可审计、可恢复、可门控的执行；ReAct 的价值以"受控循环"形式保留在节点内部，负责真正需要反馈决策的质量回路。**

## 六、Plan-and-Execute 机制深挖（追问细节）

> 面试官视角："和普通的链式大模型调用相比，'先规划后执行'在长流程创作中解决了什么核心痛点？任务规划阶段是如何做任务拆解的？"

### 6.1 相比链式调用解决的四个核心痛点

**痛点 1：创作决策漂移的级联放大**

链式调用的每一步都是"创作型"调用（高温、自由发挥），长篇小说是几十步的流水线——每一步的微小漂移都会作为输入喂给下一步，角色 OOC、伏笔错乱被指数级放大，且无法定位是哪一步引入的。

Plan-and-Execute 把"**做什么**"和"**怎么做**"两种决策拆开：

- "做什么"（路线决策）收敛成**一次**规划调用，用低温（T=0.3）、强约束（工具白名单 + JSON Schema + 依赖规则）把不确定性压到最低；
- "怎么做"（创作决策）留在执行阶段，每章生成时自由度不减。

整体熵大大降低——**规划只有一次犯错机会，而不是每一步都有犯错机会**。

**痛点 2：固定拓扑 vs 变长需求，链式做大量无用功**

链式拓扑固定：用户只是"续写第 5 章"，固定流水线也得重新跑世界观、角色、大纲——浪费 Token 且污染已有设定。规划器能感知项目已有资产（已有世界观/角色/大纲），只规划"写第 5 章"的最小步骤集，并通过 `parameters.chapter_number` 精确指定起始章。

**痛点 3：前置依赖靠模型自觉，漏了整条链崩**

链式里"必须先有世界才能有角色"只能写在 prompt 里祈祷模型记住。规划范式把依赖变成**系统硬约束**：

- 规划器输出后先做**自动修复**（`_ensure_plan_prerequisites`）：缺 world 步骤自动前插、`revise` 目标不存在降级为 `generate`、意图漂移裁剪多余步骤；
- 再做**语义校验**（`validate_execution_plan`）：`cast 依赖 world`、`chapter 依赖 outline`、`revise 必须已有角色集且 target_names 非空`、章节号 ≥1，任一不满足计划直接被拒。

流程正确性从"模型的自觉"变成"系统的保证"。

**痛点 4：失败不可定位、不可恢复**

- 计划本身是结构化、可审计的产物：失败分类明确（transport/parse/schema/validation），prompt sha256、response sha256、模型名全部记入审计清单；
- 计划整体不可用时**降级到确定性模板**，任务照样跑通；
- 附带链式没有的能力：**局部修改**——计划能表达"只重做角色林晚"（`character.revise` + `target_names`）或"重写第三章"，计划即 diff，配合 revision 体系定向修订，不推倒重来。

### 6.2 规划阶段的任务拆解流程（六环节）

**① 输入侧——给规划器两份东西**

- `raw_requirements`：用户需求原文（BriefContract）；
- `existing_summary`：项目已有设定摘要，用「世界观《》/ 已有角色 / 已有大纲」三段标记告知"哪些已存在、可直接复用"。

**② 约束侧——拆解规则写死在规划提示词里**

- **工具白名单**：仅 5 个工具（`world.generate` / `character.generate` / `character.revise` / `outline.generate` / `chapter.draft`），禁止发明新工具、必须原样带版本号；
- **步骤原子化**：一步 = 一次工具调用，每步声明 `step_id`（连续编号）、`description`、`goal`、`parameters`（结构化参数）；
- **依赖规则**：world 先于 cast/outline，outline 先于 chapter；每章正文是**独立步骤**，步骤数 = 章节数；已有设定不得重复生成；续写用 `chapter_number` 指定起始章。

**③ 结构化产出**

只允许输出内容字段 JSON，由 `PlanStep` / `ExecutionPlan`（Pydantic v2，`extra="forbid"` + frozen）解析——多一个字段、少一个字段都判 schema 失败。规划调用温度固定 0.3。

**④ 自动修复**（`_ensure_plan_prerequisites`，处理模型真实行为）

- 裸工具名补全版本号；重复 cast 步骤折叠合并；
- `revise` 但项目无角色 → 降级为 `generate`；
- 只要角色/大纲但缺 world → 自动前插；
- **意图裁剪**（`_trim_to_intent`）：outline-only 请求删除所有 chapter 步骤；"续写第 N 章"请求裁掉全部资产重建步骤、只保留章节草稿步骤。

**⑤ 双重校验**（`validate_execution_plan`）

- 结构层：非空、≤50 步、`step_id` 严格等于 1..N、工具全部已注册；
- 语义层：首步必须是 world/cast（或满足已有资产条件）、依赖链完整、`revise` 参数合法。

**⑥ 失败收口 + 图映射**

校验失败按分类记录原因（plan_info 写明 degraded 原因），返回空 → 降级到确定性意图模板（world_only / characters_only / outline_only / full_novel）。校验通过后每个步骤映射为语义节点（`world` / `cast` / `outline` / `chapter_N`），挂角色、技能、工具、验收标准、Token 预算；依赖边确定性构建——`chapter_N` 依赖 `outline` 与 `chapter_{N-1}`，保证章节严格串行继承前文。

**一句话总结**：规划阶段的价值是"**一次低温受约束的决策 + 两道确定性校验 + 自动修复兜底**"，把长流程中最易失控的部分（路径选择、依赖关系、复用策略）从每次执行中抽离，变成一份可校验、可审计、可降级、可局部修改的产物——这就是它相对链式调用的本质优势。

## 七、多轮对话处理深挖（追问细节）

### 7.1 多轮对话的本质：创作治理式对话（非闲聊）

不是"聊天式多轮"，而是"创作治理式对话"：作者在 WebUI/API 上与系统多轮交互（发起创作 → 续写 → 改设定 → 确认），每一轮都是带明确治理意图的命令。

### 7.2 run_id 内部化：多轮绑定同一 run

- 第一轮"写一本 20 章的玄幻小说" → 创建 run，产出世界观/角色/大纲/章节；
- 第二轮"续写第二章" → 自动识别为**同一 run 的延续**，不新建；
- 第三轮"把女主改成反派" → 同一 run 上的修订命令。
- 用户感知是"一个连续对话"，系统层面是"一个跨轮次持久化的运行（run）"——控制台自动管理 run_id，用户无需记住任务 ID。

### 7.3 每轮 = 一个命令（运行状态机跨轮迁移）

| 命令 | 用户意图 | 触发场景 |
|---|---|---|
| START | 发起 / 续写 | "写一本新小说" / "续写第二章" |
| PAUSE / RESUME | 暂停 / 恢复 | 需人工介入时暂停，确认后恢复 |
| CANCEL | 取消 | 本轮产出不满意，放弃 |
| REPAIR | 修复 | 质量不达标重跑 |
| REVISE | 修订 | 改角色 / 重写某章（revision 体系） |

run 状态机（queued → running → waiting_review → …）**跨轮迁移**，每轮命令推进状态，且状态迁移有合法性校验（如取消命令只能在特定状态发出）。

### 7.4 意图分派：每轮需求先被"读懂"再决定路径

- 新写意图 → 新建 run / 全量规划；
- **续写意图**（"续写第 N 章"）→ 复用已有资产，只规划新章节（`_trim_to_intent` 裁掉世界/角色/大纲重建步骤，`chapter_number` 指定起始章）；
- **修订意图**（"重做林晚"）→ 走 REVISE 定向修改，不推倒；
- **确认意图** → 对 waiting_review 产物放行。

### 7.5 资产与记忆跨轮共享

1. **资产复用**：世界观/角色/大纲存 SQLite（按项目隔离），续写轮直接加载，绝不重新生成（防漂移）；
2. **长期记忆共享**：M1-M3 正式记忆跨运行持久化，下一轮经 M4 检索注入——模型带着"上一轮的记忆"继续写；
3. **版本链延续**：修订轮的 supersedes 版本链、revision 历史跨轮累积，可追溯"设定改了几次"。

### 7.6 幂等与审计兜底

- **幂等防重**：作者重复点击/消息重发不重复执行——幂等键（run + 命令 + 输入哈希）保证同一条命令只生效一次；
- **全量审计**：每轮命令、运行事件、产物 revision、工具调用全部落库——多轮历史可完整回放。

### 7.7 典型多轮流程示例

```
第 1 轮："写一本魔法学院题材、主角是孤儿的 20 章小说" → 创建 run → 全自动生成
第 2 轮："续写第二章" → 复用资产，只生成第 2 章（chapter_number=2）
第 3 轮："重做女主" → character.revise + target_names → 角色集重建，下游章节标记失效，旧版留 revision
第 4 轮：确认 → 对 waiting_review 产物放行 → 新版本生效
```

### 7.8 与闲聊式多轮的区别 + 一句话总结

闲聊系统靠"对话历史"延续上下文（塞窗口）；本项目靠"持久化状态 + 命令语义"延续（落 SQLite）——不会因窗口爆掉而失忆，每轮精确知道是新建/续写/修订/确认，全程可回溯。

**处理方式：run 归属（run_id 内部化）+ 命令语义（状态机跨轮）+ 意图分派（续写/修订识别）+ 资产记忆复用（不重新生成）+ 幂等审计（不重不漏）。**
## 八、上下文窗口管理深挖（追问细节）

### 8.1 核心架构决策：无"持续增长窗口"，每次从零组装

闲聊式 agent 是"滚动窗口"（最近 N 轮不断追加）；本项目相反——**每一章生成从零组装一份只含"本章素材"的新窗口**：

```
写第 5 章 ≠ 窗口里塞第 1~4 章全文 + 对话
写第 5 章 = 重新组装：[第 5 章大纲节点] + [出场角色档案] + [上一章内容] + [相关记忆检索] + [文风指导]
```

30 章 = 30 次独立、恒定大小的窗口——**从架构上消灭"上下文爆炸"**。

### 8.2 ContextBuilder 按需装载（不是全量注入）

- **查询键**：本章标题 + 目标 + 计划事件（chapter.title / goal / planned_events）；
- **分类切片**：上下文分门别类（世界观片段 / 角色档案 / 前文 / 大纲节点 / 文风），每类选择性装载：
  - 世界观只注入相关片段（检索命中），非整本；
  - 角色只注入本章出场角色档案（含别名）；
  - 前文注入上一章 + 检索到的相关历史情节，非全部几十章；
  - 大纲注入本章计划节点。

### 8.3 双预算硬约束：窗口大小被契约锁死

1. **ContextPack max_tokens**：条目 token 总和 ≤ 预算，超限契约失败——硬约束；
2. **节点 budget_tokens**：章节节点独立预算（8000），执行器调用前检查。

单章成本 = 固定预算，多章总成本 = 章数 × 单章预算——**线性可控，不因历史累积超线性膨胀**。

### 8.4 作者对话不进窗口（命令沉淀为数据再经检索进入）

- 每轮命令 → 意图解析 → 更新运行状态 → 写入产物/记忆；
- 下一章生成只组装创作素材，不把作者原话带进窗口；
- 作者意图通过**持久化产物延续**：定的世界观进 WorldBible、改的角色进档案、确认的设定进 M3 记忆——**作者意图沉淀成数据，再经检索进入窗口**，而非作为对话历史累加；
- 唯一持续注入的是有界的不变内容（文风指导 style_guidance）。

### 8.5 与闲聊式 agent 上下文管理对比

| 维度 | 闲聊式 agent | 本项目 |
|---|---|---|
| 上下文形态 | 滚动窗口（最近 N 轮追加） | 每次生成从零组装（按需素材包） |
| 随轮次增长？ | 是（需摘要压缩/截断） | 否（每章窗口恒定有预算） |
| 历史延续 | 对话历史塞窗口 | 持久化产物 + 记忆检索 |
| 历史干扰 | 无关轮次污染上下文 | 相关性检索只进本章需要的 |
| 成本 | 随对话累积难控 | 章数 × 单章预算线性可控 |
| 遗忘风险 | 窗口截断丢早期信息 | M1-M3 长期记忆检索不丢 |

### 8.6 一句话总结

**不用"持续窗口"：每次生成由 ContextBuilder 按本章查询键从零组装素材包（分类选择性装载），ContextPack max_tokens + 节点 budget_tokens 双预算把窗口大小钉死在架构层面；作者多轮命令不直接进窗口，而是沉淀为产物和记忆再经 M4 检索进入——多轮再多，单次窗口恒定，不爆窗不失忆，成本线性可控。本质：把"对话历史的累积"换成"事实的持久化 + 按需检索"。**
## 九、agent loop 实现深挖（追问细节）

### 9.1 本质：三层循环嵌套

```
最外层：运行循环（run loop）      —— 调度 + 状态机 + 恢复，驱动整个 run
  └─ 中层：图执行循环（graph loop）—— 按依赖推进任务图节点
      └─ 内层：节点执行循环（node loop）—— 节点内工具序列 + 反馈回路
```

每层都有明确的推进条件和终止条件，不是 while(True) 空转。

### 9.2 最外层：运行循环（调度器 + 状态机）

- 驱动：local_run_scheduler（单 Worker）+ run_worker + run_state/run_transition；
- 流程：队列取 run → 校验租约（run_lease + fencing token 防旧 worker 竞争）→ 执行阶段（planning / execution，每阶段有超时）→ 阶段产出提交（同事务落库）→ 状态推进（queued → running → waiting_review → succeeded/failed/cancelled）→ 取下一个；
- 关键：单 Worker 串行（无并发写竞争）；租约防"死 worker 还在写"；每步提交 = 断点恢复挂载点。

### 9.3 中层：图执行循环（TaskGraphExecutor）

- 消费 NovelDomainPlugin.build_graph 的任务图（world → cast → outline → chapter×N）；
- 流程：计算可执行节点（依赖完成 & 未执行）→ 执行 → 验收（acceptance：world_schema_valid / continuity_ok / quality_accept）→ 通过则提交，失败走 REPAIR/REVISE 或暂停 → 循环到无可执行节点；
- 关键：DAG 依赖（chapter_N 依赖 outline + chapter_{N-1}，严格串行继承前文）；**图的推进由验收驱动，不是"执行完"驱动**；计划或模板产图统一，执行循环无差别。

### 9.4 内层：节点执行循环（受控 ReAct）

驱动：ChapterExecutionWorkflow（章节节点执行器），唯一有反馈回路的循环：

```
loop（最多 max_repairs + 1 次）：
  generate 草稿（chapter.draft，REPAIR 轮走 chapter.repair）
  → stage 草稿（落库成证据源）
  → 抽记忆（memory.extract → 候选入 M0）
  → 审计（continuity.audit）
  → 评审（quality.evaluate）
  → 决策：ACCEPT → 提交（accept_chapter，记忆转正）→ 结束
          REPAIR → 带 failure_codes 定向修订重生成
          PAUSE  → 暂停等人工
          EVALUATOR_ERROR → 失败处理
```

- 关键：生成→审计→评审，工具结果反馈决策（受控 ReAct）；**次数有界（max_repairs=2）绝不无限循环**；REPAIR 轮带旧草稿证据（revision + sha256）+ failure_codes，修复有依据；终止只有三种——ACCEPT / PAUSE / 预算耗尽。

### 9.5 失败处理贯穿三层

| 层 | 失败类型 | 处理 |
|---|---|---|
| run loop | provider 故障 / 超时 | 失败分类 → 重试/切换模型；阶段超时 → 标记失败可恢复 |
| graph loop | 节点验收不过 | REPAIR / REVISE / 暂停人工，不硬闯 |
| node loop | 评审不过 / 格式错 | 定向修订（≤2 次）/ EVALUATOR_ERROR 暂停 |
| 任意层 | 进程崩溃 | 租约失效 + 断点恢复：从最后已提交阶段/节点继续 |

### 9.6 与标准 agent loop（ReAct 式）区别

| 维度 | 标准 agent loop | 本项目 agent loop |
|---|---|---|
| 决策点 | 模型每步自主（思考→行动） | 路径由规划器一次决定，执行按图推进 |
| 循环主体 | 模型 + 工具反馈 | 系统状态机 + 任务图 + 门控 |
| 终止条件 | 模型自己觉得"完成" | 明确验收标准 + 预算上限 |
| 可恢复性 | 状态在对话里，难恢复 | 每步提交，断点续跑 |
| 可审计 | 弱 | 每步留痕 |

### 9.7 一句话总结

**agent loop 是三层嵌套的治理循环：run loop（调度+状态机+租约+断点恢复）→ graph loop（DAG 依赖+验收驱动）→ node loop（受控 ReAct：生成→审计→评审→修复，max_repairs=2 封顶）；模型只负责每步生成，循环的推进、验收、恢复、终止全部由系统控制——本质是把"模型自主循环"改造成"系统治理循环"。**
## 十、PlanAct 对比深挖（opencode / Codex 对标）（追问细节）

### 10.1 相似点（诚实承认）

1. **都是 Plan 先行**：不让模型"裸跑"——先显式化计划（它用 todo 列表，本项目用执行计划/任务图），再执行；
2. **都是"执行 → 观察 → 修订"闭环**：Codex 看测试/诊断后改代码重跑；本项目节点看审计/评审结果定向修订——都是反馈驱动，不是单向流水线；
3. **都有降级/兜底**：它计划失效会重新规划；本项目计划失效降级确定性模板；
4. **都强调可恢复**：它靠会话/checkpoint 续跑；本项目靠每步提交断点续跑。

**如果只说"Plan 一下再 Act，Act 完看结果再 Plan"，那与 opencode/Codex 确实是同一家族。**

### 10.2 本质区别

| 维度 | opencode / Codex（PlanAct） | 本项目 |
|---|---|---|
| 计划产生者 | 模型执行过程中**动态**生成/修订计划（每轮都可能改 todo） | 运行前**一次性**生成（规划器），执行期固定 |
| 计划粒度 | 细粒度逐步（任务拆成原子动作） | 粗粒度按阶段（世界→角色→大纲→章节，节点内再拆） |
| 计划可变性 | **高**（发现问题就改计划） | **低**（变化走 REVISE 人工命令，不走模型自主改） |
| 决策主体 | 模型在"做"与"调整计划"间自主选择 | 模型只"做"，"是否调整"由系统门控（验收/审计/评审）决定 |
| 循环终止 | 模型自己判断"完成" | 明确验收标准 + 预算上限，系统判定 |

**一句话：opencode/Codex 是"模型主导的动态 Plan-Act 循环"；本项目是"系统主导的固定 Plan + 受控 Act 循环"。**

### 10.3 为什么设计成"固定计划"（差异根源）

1. **任务可预测性不同**：写代码高度不确定（bug 藏哪、API 什么样），必须边做边探——动态计划是刚需；小说创作是强领域先验（世界→角色→大纲→章节），路径基本确定；
2. **一致性约束**：Codex 目标是局部正确性；小说是几十章累积一致性——模型每章自主改方向，角色/伏笔/时间线第 5 章就漂掉，方向决定权必须收走；
3. **质量门控需要固定节点**：验收/审计/评审挂固定节点保证每章走同一套门；动态计划使门的位置变化，质量无基线；
4. **成本可控**：动态计划 = 模型每步决策 = 调用多且不可预期；固定计划 + 节点预算 = 线性可控；
5. **保留了动态修订出口**：需要改方向走 REVISE 命令（人工触发）——把"自主改计划"降级为"受控改计划"，是 PlanAct 思想在场景约束下的妥协版。

### 10.4 结论：同一家族，不同分支

**是同一个范式的不同侧重：opencode/Codex 是"模型主导、动态、探索型"的 PlanAct；本项目是"系统主导、固定、执行型"的 PlanAct。两者都先规划后执行、都有反馈修订——区别在于"计划由谁改、多久改一次、改的权限在谁手里"。**

面试表达建议：直接说"是 PlanAct 家族，但我把它从'模型动态规划'改造成了'系统固定规划 + 受控反馈'"——既展示懂业界架构，又讲清差异化设计。

### 10.5 一句话总结

**本项目与 opencode/Codex 同属 PlanAct 家族（先规划后执行、反馈修订、可恢复），但把"模型动态规划"改造成"系统固定规划 + 受控反馈"：计划运行前一次性生成、执行期固定，调整走 REVISE 人工命令而非模型自主改，终止由验收标准和预算决定——适合强领域先验、需长周期一致性的场景；做不确定探索型任务时则应当回到 opencode/Codex 式的动态 PlanAct。**
## 十一、记忆系统口头介绍（面试口语版）

> 面试官视角："你的跨章节记忆系统是怎么设计的？"——此版本不含任何代码细节，只讲设计思路，与简历描述一致。

我这个项目的记忆系统，核心要解决一个问题：**一本小说要写几十章，怎么保证模型"记得住、不写乱、不写错"**。我的方案是一套分层的记忆管理体系，加上一条严格的存储流水线。

**先讲分层。** 我把记忆分成六层，从"最不可信"到"最可信"：

- 最底层是**候选层**：模型每章写完，系统自动把新出现的人物、设定、情节线索抽成一条条"事实"，比如"林晚是女主"、"大陆分为七国"。这一层的东西**默认不可信**，不允许直接参与后续生成；
- 往上是**规范层**和**计划层**：规范层存的是跨章节通用的设定事实，比如人物档案、世界设定；计划层存的是跟大纲绑定的剧情走向，比如"第三章女主觉醒"；
- 再往上是**确认层**：经过作者人工确认过的事实，可信度最高，是系统判定冲突时的最高依据；
- 最上面两层是**检索层**和**工作层**：检索层不是存储，而是"递话层"——每次写新章节前，系统从可信层里挑出这一章真正相关的记忆，组装成一份带 Token 预算的上下文包喂给模型；工作层是单次运行内的临时状态，跑完就回收。

这套分层的核心价值是**物理隔离**：新产生的信息永远先落在候选层，和已确认的事实隔离开，不会静默覆盖旧设定。

**再讲一章小说里，记忆具体是怎么存进去的。** 完整链路是"抽取 → 挂证据 → 进候选 → 审计 → 验收 → 转正"六步：

第一步，**抽取**。章节正文生成完，系统先不急着存，而是做一次结构化抽取，把这一章新出现的人物、设定、伏笔整理成"主语-谓语-宾语"这种事实三元组——存事实而不是存整章摘要，因为事实粒度才能精确检索、精确比对、精确更新。

第二步，**挂证据**。每条事实必须绑定来源：它出自哪一章的哪一段原文。系统会存下原文片段和它的内容哈希，并且校验这个片段确实能在那一章里找到、确实属于当前作品。**无来源、对不上号的事实直接丢弃**——这一步是防幻觉的关键，模型说错了没关系，系统不允许没有原文支撑的信息入库。

第三步，**进候选区**。校验通过的事实写入候选层，同时做了内容寻址去重：同一事实、同一来源，天然是同一个 ID，重复抽取自动合并，不会在库里堆一堆重复条目。

第四步，**连续性审计**。接下来系统拿这一章的内容跟已确认的记忆做比对，查三类问题：角色行为有没有偏离设定（OOC）、时间线和伏笔跟前面有没有矛盾、新设定跟世界观冲不冲突。审计发现硬冲突，这一章直接进入等待人工处理的流程，不会带病往下走。

第五步，**质量评审**。无冲突的章节再走质量打分，过关才进入验收。

第六步，**验收转正**。这是最关键的一步：**只有章节验收定稿，它的候选记忆才会被提升为正式记忆**。没定稿的章节，它的记忆永远躺在候选区，不参与后续任何生成。所以"半成品的内容污染后面的正文"这件事，在流程上就被堵死了。

**最后讲怎么读。** 写下一章之前，系统不是把全部记忆都塞进去——上下文窗口装不下几十章，也容易互相干扰。而是做**按需检索**：根据这一章要写的内容，从可信层挑出相关的记忆条目，组装成一份有 Token 上限的上下文包注入。模型每一章看到的，都是"这一章真正用得上的前文事实"，而不是一个塞不下的历史包袱。

另外还有一条补充路径：如果作者中途要改设定，比如"把女主改成反派"，系统不会覆盖旧记忆，而是**生成一个新版本的事实，并显式标记它取代了旧版本**——新旧版本都在库里，可追溯、可回退，最后由作者确认后新版本才生效。所有记忆都存在 SQLite 里，跨运行持久化，续写新章节时自动复用，重启也不丢。

总结一句话：**先抽事实、再挂证据、进候选隔离、审计查冲突、验收才转正、按需注入使用**。这套流程保证模型在几十章的连载里，该记住的忘不掉，新写的不会和旧设定打架，幻觉和半成品也污染不了正式的记忆库。

## 十二、记忆系统技术深挖（追问细节）

### 12.1 M0-M5 六层架构

设计原则：**信息越往上越可信、越精简、越可被直接使用；越往下越原始、越带噪、越需要证据支撑**。

| 层 | 名称 | 存储什么 | 进入方式 | 角色 |
|---|---|---|---|---|
| **M0** | 候选层 | 每章抽取的原始记忆候选（事实三元组 + 证据） | 章节产出后由抽取器产生，`stage_memory_candidates` 落库 | 隔离带：未确认信息不许进入正文生成 |
| **M1** | 规范层 | 跨章节共用的规范事实（人物设定、世界设定） | 候选经提升（promotion）成为正式记录 | 事实库：后续章节的"设定依据" |
| **M2** | 计划层 | 与规划/大纲绑定的事实（剧情走向、章节计划） | 随大纲/计划产物提交，状态 validated | 计划事实：约束章节执行方向 |
| **M3** | 确认层 | 经人工确认的事实 | 作者确认门控后进入，状态 confirmed | 最高可信度：作者背书的定稿事实 |
| **M4** | 检索层 | 从 M1-M3 选取并组装出的上下文包（ContextPack） | 生成章节前按相关性实时组装 | 视图层：不是存储，是"递给模型的记忆" |
| **M5** | 工作层 | 单次运行期的工作记忆（当前任务上下文快照） | 运行期临时维护 | 运行态：跨步骤传递、运行结束后回收 |

两个契约级约束：

1. **候选必须留在 M0**（"candidates must remain in M0"）——模型抽取的东西再像事实，没验收之前永远进不了正式层；
2. **正式记录只允许 M1/M2/M3**（"records must use a promotable memory layer"）——M4/M5 是组装出来的视图，不允许被当作事实直接写入。

记忆的**原子单元是事实三元组**（subject/predicate/value，如"林晚 / 是 / 女主"），而不是整章摘要——事实粒度才能支持精确检索、冲突比对和定向更新。

### 12.2 单章生成的记忆存储时序（8 步）

正常生成一章时，`ChapterExecutionWorkflow` 的记忆存储链路：

1. **激活章节任务**：任务 `pending → running`，写 `tasks` 表并记 `task_started` 事件；全程受 RunLease（租约 + fencing token）保护，所有写入在同一 SQLite 事务内原子提交（产物 + 记忆 + 事件）；
2. **生成草稿**：经工具网关调 `chapter.draft@1.0.0`（REPAIR 轮次走 `chapter.repair@1.0.0`），角色 CHAPTER_EXECUTOR；
3. **草稿落库成"证据源"**：`stage_chapter` 写 `artifacts` 表（artifact_id、revision、status、raw_bytes + raw_sha256）——之后所有记忆必须锚定到这个已落库产物；
4. **抽取记忆候选**：调 `memory.extract@1.0.0`（角色 MEMORY_EXTRACTOR），输出 `MemoryProposal` 列表：事实三元组 + 证据锚点（source_artifact_id / revision / 字节区间 / source_excerpt）+ `extraction_schema_version` + `normalized_fact_hash()`；
5. **候选入库 M0**：`stage_memory_candidates` → `stage_candidates` 写 `memory_candidates` 表。**入库存证五重校验**（`load_source` + `build_evidence`）：来源产物存在（SOURCE_NOT_FOUND）/ 属于当前项目（SOURCE_NOT_ELIGIBLE）/ sha256 一致（SOURCE_INTEGRITY）/ 区间与原文吻合（SOURCE_SPAN_INVALID）/ 文本产物（SOURCE_NOT_TEXT）。通过后按内容寻址派生 `candidate_id` = hash(产物ID + revision + 抽取版本 + 归一化事实哈希)——同一事实同一来源天然同 ID，自动去重；
6. **连续性审计**：调 `continuity.audit@1.0.0`（CONTINUITY_AUDITOR），与 M1-M3 已确认记忆比对，产出 `ContinuityAuditReport`（located_beats + hard_conflicts）；
7. **质量评审**：存在硬冲突直接返回 PAUSE（reason: continuity_hard_conflict），不浪费评审调用；无冲突才调 `quality.evaluate@1.0.0`（QUALITY_REVIEWER），产出 ACCEPT / PAUSE / REPAIR 并落库（`record_chapter_quality`）；
8. **验收提交（记忆转正）**：`accept_chapter` → `commit_chapter_acceptance` 同一事务完成：章节产物 status → `accepted`；**M0 候选随来源产物验收提升为 `memory_records`（M1 规范层，status canonical）**，并维护 `supersedes_memory_id` 版本链。

**关键设计：候选先于验收入库、但提升严格后置于验收**——草稿没定稿，记忆永远停留在 M0，不污染后续章节生成上下文。

三条不同的写入路径：

| 层级 | 写入路径 | 时机 |
|---|---|---|
| **M1 规范层** | 章节验收时从 M0 候选提升 | 每章验收通过后 |
| **M2 计划层** | 大纲/计划产物提交时写入（planning_memory_commit），状态 validated | 规划阶段 |
| **M3 确认层** | 人工确认门控（artifact_approval_required / waiting_review 后作者确认）后提升，状态 confirmed | 人工介入时 |

存储之后的读取：下一章生成前，检索器从 `memory_records`（M1-M3）按相关性组装 `ContextPack` 注入——每条 `ContextItem` 带 token_count，`ContextPack` 有 max_tokens 硬预算校验（超限契约失败）。读到的是"事实 + 证据引用"，不是摘要。

### 12.3 记忆遗忘 / 冲突 / 污染的解法

**遗忘（上下文窗口装不下几十章）**

1. **持久化不依赖上下文存活**：SQLite 内容寻址存储，跨运行、跨进程存在；续写从库里加载，运行断了记忆不丢；
2. **事实化抽取对抗压缩损耗**：存三元组而非整章摘要，每条设定独立存在、可精确检索，不因压缩丢失；
3. **按需检索注入（M4）**：每章前从 M1-M3 挑相关记忆组装带预算上限的 ContextPack，模型上下文里永远有"这一章真正需要的前文事实"；
4. **证据溯源可回滚**：每条记忆锚定来源产物字节区间 + sha256，模型侧摘要退化时可从原文完整恢复。

**冲突（新事实与已确认事实矛盾）**

1. **层间隔离先隔离再裁决**：新内容永远先落 M0，未确认新信息不会静默覆盖旧事实；
2. **显式超承（supersedes_memory_id）**：新事实取代旧事实时生成新记录并链接旧记录，形成版本链而非就地覆盖，可追溯、可回退；
3. **连续性审计自动检测**：角色 OOC / 时间线错乱 / 伏笔矛盾 / 设定冲突，审计不过 → quality_accept 失败 → REPAIR/REVISE 定向修订，只重写冲突段落；
4. **人工确认最终裁决**：M3 需作者门控确认，语义级冲突由作者拍板；
5. **验收门控卡住冲突源头**：章节只有验收通过才提升记忆，没定稿的内容不污染后续生成。

**污染（幻觉、来源不可靠、重复生成出不同版本）**

1. **证据完整性强制校验**：五重校验（见 12.2 第 5 步），无证据、对不上号的记忆直接拒绝——不允许没有原文支撑的幻觉入库；
2. **内容寻址去重**：候选/记录 ID 由「来源 + revision + 抽取版本 + 归一化事实哈希」派生，同一事实同一来源天然同 ID，重复抽取自动合并；
3. **角色名归一化**：人名偏差（"李明" vs "李铭"）相似度匹配归一到已有档案，防角色碎片化；
4. **复用而非重建防漂移**：续写只生成缺失资产（世界观/角色/大纲已存在则跳过），杜绝同一事实被多次生成出不同版本（规划层 `_trim_to_intent` 实现）。

**一句话总结**：M0-M5 分层把记忆管理做成"**候选隔离 → 证据背书 → 门控提升 → 检索按需注入 → 版本化超承**"流水线——遗忘靠持久化 + 事实化 + 按需检索，冲突靠分层隔离 + 审计检测 + 人工裁决，污染靠证据校验 + 内容寻址去重 + 复用防漂移。

## 十三、记忆膨胀问题口头介绍（面试口语版）

> 面试官视角："记忆系统会不会随着内容越来越多而无限膨胀？怎么处理？"——不含代码细节，只讲设计思路。

这个问题我把"膨胀"拆成两件事：**模型看到的记忆（注入侧）** 和 **库里存的记忆（存储侧）**，两边的处理完全不同。

**先讲模型看到的（注入侧）——不会膨胀，因为有两道闸。**

1. **相关性过滤**：每次写新章节前，系统不是把记忆库全量塞给模型，而是根据这一章要写什么，只挑出相关的记忆条目；
2. **预算封顶**：挑出来的记忆组装成上下文包时，有严格的 Token 上限，超了就装不下。

所以哪怕库里积累了一万条记忆，模型每一章看到的量是**恒定**的——上下文窗口永远不会被历史撑爆。

**再讲库里存的（存储侧）——会增长，但有效记忆受控。**

诚实承认：每章新角色、新设定必然产生新记忆，库会变大，这是有意义的增长。但系统有五层机制防止失控：

1. **去重**：同一条事实、同一个来源，物理上只存一份，重复抽取不产生重复条目——直接把"重复膨胀"掐死；
2. **取代链**：新事实取代旧事实（比如作者改了设定）时，显式标记"新版本取代旧版本"。模型看到的永远是当前有效版本，被取代的旧版本退出使用、只留作审计和回退——"有效记忆"不随修改次数叠加；
3. **候选隔离**：每章抽取的记忆先进隔离区，只有章节验收定稿才转正。库里可能有大量没转正的半成品记忆，但它们对生成零影响——相当于蓄水池，只放行经过验收的水；
4. **入库有裁决**：每条候选不是自动转正，而是经过策略层裁决——正常转正、需人工复核、还是冲突挂起。不是所有抽出来的东西都能成为正式记忆；
5. **按需使用**：前面的检索和预算，让"库有多大"和"模型看多少"彻底脱钩。

**最后诚实说边界**：有两种数据确实会累积——被取代的旧版本、旧版大纲留下的规划记忆。但它们有一个共同点：**只占存储、不参与生成、不影响质量**。这类"审计性数据"适合用生命周期策略定期归档清理，这是系统的演进方向；当前优先级是先保证可追溯，再谈清理。

一句话总结：**注入侧靠"相关性检索 + 预算封顶"永不膨胀；存储侧靠"去重 + 取代链 + 候选隔离 + 入库裁决"让有效记忆受控增长；不可避免的累积是审计性数据，不参与生成，走生命周期管理。核心思想：存储可以大，但每次使用必须小且准。**

## 十四、记忆膨胀问题技术深挖（追问细节）

### 14.1 先拆问题：两个"膨胀"

| | 注入膨胀（模型上下文） | 存储膨胀（SQLite 事实库） |
|---|---|---|
| 现象 | 喂给模型的记忆越来越多 | 库里的事实条目越来越多 |
| 危害 | 上下文爆窗、无关信息干扰生成 | 检索变慢、冲突变多、成本上升 |
| 系统策略 | **硬预算封顶** | **增长受控 + 有效集收敛** |

### 14.2 注入侧：永不膨胀（相关性检索 + 硬预算）

1. **相关性检索**：以当前章节标题/目标/情节节点为查询键，走全文索引（`memory_fts`）按相关性取 top-k，只挑这一章真正用得上的事实；
2. **Token 硬预算**：`ContextPack` 有 `max_tokens` 上限，契约层强制校验"条目 token 总和 ≤ 预算，超限契约失败"——硬约束而非软提醒。

膨胀被转移到存储侧，而存储侧的膨胀是受控的——**注入量与存储规模彻底解耦**。

### 14.3 存储侧：六层机制控制"有效记忆集"

1. **内容寻址去重（防重复膨胀）**：`candidate_id = hash(来源产物 + revision + 抽取版本 + normalized_fact_hash)`，入库 `ON CONFLICT DO NOTHING`——同一事实同一来源物理上只存一条；`normalized_fact_hash` 归一化（kind/predicate/subject_id/目标层/value），"同一事实不同表述"也能对上；重复抽取只刷新证据不新建条目；
2. **supersedes 版本链（防新旧并存膨胀）**：新事实经 `supersedes_memory_id` 显式取代旧记录；冲突检测查询模式 `NOT EXISTS(successor.supersedes_id = current.memory_id)`——**被取代记录不参与检索**，有效记忆集随修订收敛而非叠加；旧记录仅为审计/回退保留；
3. **候选生命周期（防半成品膨胀）**：候选状态机 QUARANTINED → NEEDS_REVIEW / CONFLICTED / PROMOTED；未验收章节的候选留在隔离区不进入检索；提升后标记 PROMOTED 防重复处理；
4. **策略层裁决（防无原则入库）**：`decide_promotion` 裁决每条候选——PROMOTED / REVIEW_REQUIRED / CONFLICTED（带 `requires_pause`），不是所有抽取内容都能转正；
5. **检索相关性过滤（防检索集膨胀）**：有效记忆再多，每次只取 top-k 相关子集 + Token 预算约束——存储规模与注入规模解耦；
6. **M5 工作记忆回收（防临时态残留）**：运行期临时状态，运行结束即回收，不持久化。

### 14.4 诚实的边界：什么会真的累积

1. **被取代的旧记录**（supersedes 链上的历史版本）——可追溯性的代价，不参与检索但占用存储；适合生命周期策略（定期归档/清理/摘要化），当前系统优先保证可追溯，清理是演进方向；
2. **不同 plan revision 的规划记忆**——规划记忆稳定 ID 含 `plan_revision`（如 `world:{id}` 含 revision），大纲每修订一版写入新记录，旧版保留——审计性膨胀，走 revision 级清理策略。

两类累积共同点：**只占存储、不影响生成质量**——注入侧预算封顶 + 检索相关性过滤，决定了"库里有什么"和"模型看到什么"完全解耦；真正的质量风险（无关记忆混入上下文）已被 M4 相关性检索 + 预算挡住。

### 14.5 一句话总结

**注入侧靠"相关性检索 + Token 硬预算"永不膨胀；存储侧靠"内容寻址去重 + supersedes 有效集收敛 + 候选隔离 + 策略层过滤"让有效记忆受控增长；不可避免的累积（被取代记录、旧 revision）是审计性数据，不参与生成，走生命周期管理。核心设计思想：存储可以大，但每次使用必须小且准。**

## 十五、记忆存储边界深挖（追问细节）

### 15.1 存储判断四原则

1. **结构化事实才存，原始文本不存**：记忆单元是三元组（可检索、可比对、可更新），不是整章原文或对话流；
2. **有证据的才存，无来源的不存**：每条事实绑定来源（哪一章哪段原文 + 哈希），模型"随口说的"一律不存；
3. **验收过的才转正，半成品只进候选**：未定稿章节的记忆不参与任何生成；
4. **当前有效才参与检索，被取代的退出**：supersedes 版本链决定"有效记忆集"。

### 15.2 要存储的内容（五类）

| 类别 | 层 | 例子 |
|---|---|---|
| 世界设定事实 | M1 | "大陆分为七国"、"魔法体系以元素为核心" |
| 角色身份档案（入库前名字归一化，"李明/李铭"归一到同一档案） | M1 | "林晚是女主，性格清冷，与主角是义兄妹关系" |
| 剧情规划事实（随大纲/计划产物提交） | M2 | "第三章：女主觉醒"、"第五章埋下'钥匙'伏笔" |
| 关键情节事件（带时间确定性） | M1/M3 | "林晚在第三章觉醒了冰系能力" |
| 作者确认事实（最高可信度，冲突裁决依据） | M3 | "作者确认：女主最终不会黑化" |

外加一类**审计性数据**（被取代版本、调用台账、prompt/response 指纹）——要存，但为了可追溯，不为生成。

### 15.3 不存储的内容（八类）

| 不存储 | 原因 |
|---|---|
| 模型与系统的完整对话流 | 原始往返无法检索比对——只存结构化抽取结果；原始 prompt 只存 sha256 指纹 |
| 整章原文/整章摘要作为记忆 | 原文是 artifacts 产物自有存储；摘要式记忆有损且不可比对 |
| 运行期临时状态（M5） | 运行结束即回收，存了就是垃圾数据 |
| 组装好的上下文包（M4） | 用完即弃，每次按需重新组装 |
| 未验收章节的候选记忆 | 物理在 M0 隔离区，功能上不参与生成 |
| 冲突未裁决的内容 | CONFLICTED 挂起，既不转正也不注入 |
| 被取代的旧版本 | 退出检索（模型层遗忘），只留审计 |
| 一次性/临时角色细节、文学性描写 | 抽取器入口过滤（is_NPC 开关区分核心/路人角色）——记忆只收"会影响后续创作的事实" |

### 15.4 决策口诀（四问）

```
① 是事实吗？      → 结构化三元组？（寒暄/描写/情绪词 → 淘汰）
② 有来源吗？      → 能锚定到某章某段原文，证据校验通过？（模型自述 → 淘汰）
③ 验收了吗？      → 所属章节已定稿、候选已过冲突检测和策略裁决？（半成品 → 只进候选区）
④ 还当前有效吗？  → 没有被更新的版本取代？（被取代 → 退出检索，只留审计）
```

四问全过 → M1-M3 可用记忆；任何一问不过 → 淘汰 / 隔离 / 降级。

### 15.5 不存储内容的五条处置路径

| 路径 | 处理内容 | 核心机制 |
|---|---|---|
| A 入口拦截（从未入库） | 临时角色细节、文学性描写、寒暄 | 抽取 schema 只收事实；名字归一化入口合并 |
| B 用完即弃（内存态） | M4 上下文包、M5 工作记忆 | 存 context_digest 指纹不存内容；运行结束回收 |
| C 隔离滞留（候选区） | 未验收候选 | 物理落库功能隔离；证据随产物状态刷新；生命周期清理（演进方向） |
| D 挂起待裁（冲突区） | 冲突未裁决事实 | CONFLICTED + requires_pause 暂停等人工裁决，裁决后转正或丢弃 |
| E 降级保留（审计区） | 被取代旧版本、原始 prompt | supersedes 退出检索物理保留；prompt 指纹 + 模板版本重建全文 |

统一哲学：**能拦就拦、该丢就丢、留而不放、疑而不决、降而不删**；每条处置路径都有状态记录和事件留痕，处置过程可观测。

### 15.6 边界案例

1. **临时角色**：抽取时区分核心/路人角色，路人细节不提升为核心记忆（防一次性信息污染）；
2. **时间性事实**：带时间确定性的情节事实超过时效即失效，靠 supersedes 或时效规则退出检索——防止"过时的真话"变成"现在的错误"；
3. **推断 vs 观察**：记忆模型区分"模型直接观察的事实"和"模型推断的结论"（InferenceMode），推断类可信度更低，更依赖证据和确认。

### 15.7 一句话总结

**存的是"结构化、有证据、已验收、当前有效"的创作事实（世界/角色/大纲/情节/确认），不存的是"原始文本、临时状态、半成品、冲突未决、被取代版本"；判断标准四个问题：是事实吗？有来源吗？验收了吗？还有效吗？**
## 十六、候选区机制深挖（追问细节）

### 16.1 候选生命周期状态机（五条去向）

```
入库（QUARANTINED 隔离，默认态）
  ├─→ PROMOTED（转正）：验收通过 → 冲突检测 + 策略裁决通过 → 提升为正式记忆，候选标记防重复处理
  ├─→ NEEDS_REVIEW（待复核）：策略层裁决需要人工确认
  ├─→ CONFLICTED（冲突挂起）：与正式记忆矛盾 → requires_pause 触发暂停等人工裁决
  ├─→ 滞留：章节未验收/被放弃 → 永远停在 QUARANTINED，不参与任何生成
  └─→ 证据刷新：来源产物状态变化时，候选证据同步刷新（refresh_candidate_evidence）
```

三个关键机制：

1. **转正即标记**：提升后候选状态改 PROMOTED（不删除），同源同事实新 proposal 走"已有转正"短路，不重复提升；
2. **重复抽取即合并**：新候选入库前查同源 + 同归一化事实哈希（`_candidate`），命中不新建、只刷新证据；
3. **证据绑定产物状态**：候选证据随来源产物状态刷新（`refresh_candidate_evidence` 更新 source_status、校验不可变部分）——来源产物失效的候选无法转正，等于自动过期。

### 16.2 清理策略：全盘保留 vs 定期清理（诚实回答）

**现状：全盘保留，无定期清理任务**（代码中无定时清理/保留策略）。候选记录留在 memory_candidates 表，直到被提升、人工处理、或来源产物生命周期结束。

三重防膨胀机制：

1. **入库去重**：同源同事实物理上只有一条（ON CONFLICT DO NOTHING + 归一化哈希命中即刷新）；
2. **状态收敛**：转正标记 / 冲突挂起 / 滞留隔离——记录数量随章节数线性增长，不因重复而超线性增长；
3. **证据失效即"逻辑清理"**：来源产物被取代/失效的候选，证据刷新后无法转正，功能上已"死"。

**合理清理时机（演进方向）**：来源产物已失效（永远无法转正）→ 可安全清理；存储敏感场景按"状态 + 时间 + 来源失效"归档；清理前留痕（审计不断）。当前优先级是"先保证可追溯"。

### 16.3 隔离候选不会导致新增记忆存储错误（旁观者不是阻塞者）

四个机制层面的论证：

1. **不参与冲突检测**（`_has_conflict` 只查 memory_records 当前有效记录）→ 不会产生"假冲突"，不会误阻新记忆入库；
2. **复合精确键不占位**（来源 + revision + 抽取版本 + 归一化事实哈希）→ 新事实哈希不同永远开新行；同来源同事实走刷新（去重语义，非错误）；
3. **转正判定每次重新执行**（ingest → decide_promotion 重跑）→ 隔离不是"永久否决"，后续验收通过仍可转正；
4. **证据刷新有完整性校验**（SOURCE_INTEGRITY）→ 宁可报错，不会用错误数据覆盖已有候选。

对新增记忆的影响面：**不影响"提取"**（抽取器输入是本章草稿，候选区不参与抽取提示词）；**直接影响"存储"**——去重短路（同源同事实刷新不新建）、转正短路（PROMOTED 直接返回已有结果）、冲突检测上下文。

三个诚实边界：① 同事实多来源产生多条候选/记录（证据锚定 vs 全局去重的取舍，检索重复返回有小冗余，跨来源全局去重是优化方向）；② 隔离候选无清理 → 存储线性增长（只影响规模不影响正确性）；③ 来源被篡改 → 报错而非静默（保护机制）。

### 16.4 保留隔离候选的意义（为什么不清除）

1. **可追溯（"拒信档案"）**：回答"这个设定为什么不在正式记忆里"——区分模型没抽到（抽取缺失）/ 抽到没验收（隔离）/ 验收被取代（supersedes），这是记忆系统的故障诊断能力；
2. **裁决可逆**：隔离是"时机未到"不是"内容错了"——章节修复后重新验收时，同源候选刷新并重新裁决转正；删掉则丢失 review_code 和冲突历史，裁决失忆；
3. **去重索引**：隔离候选是去重机制的一部分，删了反而导致重复抽取反复新建；
4. **生命周期一致**：候选绑定来源产物 revision，产物在候选在；产物被取代后候选自然失效——清理时机跟随产物生命周期。

直接清理的坏处：丢审计 / 破去重 / 裁决失忆 / 复杂度换不来收益（候选是小结构化记录、不参与检索不占性能——空间论据几乎为零）。

正确策略：**保留（可追溯）→ 随来源产物失效清理（安全点）→ 清理前留痕（审计不断）**——不是"立即清理"，也不是"永久全盘保留"。

### 16.5 一句话总结

**候选区不是被动仓库，而是"去重索引 + 状态裁决器"：转正的标记、冲突的挂起、滞留的隔离、证据随产物刷新；隔离候选是旁观者不是阻塞者（不产生假冲突、不占位、不永久否决）；保留的意义是"拒信档案"（可追溯 + 裁决可逆 + 去重索引 + 故障诊断），清理的合理时机是随来源产物失效而非立即删除。**
## 十七、记忆存储崩溃一致性深挖（追问细节）

### 17.1 三层防线：为什么"记忆存一半"不存在

1. **事务原子性（根本防线）**：所有记忆写入包在 write_transaction 中——候选入库单事务；转正提交（INSERT memory_records + UPDATE memory_candidates 标记 + INSERT memory_fts）三写单事务。中断即整体回滚：记忆写入只有"完成"和"未发生"两种状态；
2. **产物先行（顺序防线）**：候选入库依赖来源产物已落库（load_source 校验 sha256）——中断只会出现"产物在、记忆无"，不会出现半条记忆或悬空记忆；
3. **幂等重放（恢复防线）**：候选入库 ON CONFLICT DO NOTHING、记录入库 ON CONFLICT(memory_id) DO NOTHING；恢复器只重放未完成节点——恢复 = 重放 + 去重，不丢不重。

### 17.2 四种中断场景

| 场景 | 中断点 | 结果 | 恢复处理 |
|---|---|---|---|
| A | 候选入库事务内 | 事务回滚，无候选写入 | 节点重放，重新抽取重新入库（幂等） |
| B | 转正提交事务内（三写） | 整体回滚，候选保持原状态 | 重新执行验收提交，三写再走一遍 |
| C | 产物已提交、记忆未开始 | 产物在、记忆无 | 节点重放：产物已存在跳过生成（幂等），只补记忆 |
| D | 数据库文件级损坏（极端） | SQLite 日志机制崩溃恢复 | 证据五重校验拒收任何不一致数据 |

### 17.3 三道兜底（即使极端出现不一致）

1. **状态机检测**：run 状态非 succeeded → 走恢复流程，不信任半成品状态；
2. **校验拒收**：候选/记录证据带 sha256 + 字节区间，加载五重校验（SOURCE_NOT_FOUND / SOURCE_INTEGRITY / SOURCE_SPAN_INVALID 等）——不一致数据报错而非静默通过；
3. **审计定位**：run_events 运行事件流记录每一步提交——中断点精确定位，恢复器据此决定重放起点。

### 17.4 一句话总结

**记忆存储的可靠性不是"写的时候小心"，而是"写的方式保证原子（单事务）、恢复的方式保证幂等（内容寻址去重）、校验的方式保证干净（证据五重校验）"——事务 + 产物先行 + 幂等重放三层防线让"存一半"在设计上不存在，状态机 + 校验拒收 + 事件流三道兜底覆盖极端损坏。**
## 十八、工具调用口头介绍（面试口语版）

> 面试官视角："你的工具调用是怎么设计的？怎么保证 agent 不乱调工具？"——不含代码细节，只讲设计思路。

我的工具调用设计，核心目标就一句话：**让模型"想干什么"必须走系统"允许干什么"的那条路，除此之外没有第二条路**。拆成四个方面：有什么工具、怎么设计的、一次调用怎么跑、怎么保证不乱调。

**有什么工具。** 整个创作流程只暴露了九类操作，分三组：

- **创作类**：生成世界观、生成角色、定向重做角色、生成大纲、写章节正文、定向修订章节——"动手写"的工具；
- **记忆类**：抽取记忆——每章写完后把人物、设定、伏笔抽成结构化事实；
- **检查类**：连续性审计、质量评审——"只看不动手"，纯只读。

**怎么设计。** 每个工具是一份完整"档案"，写清六件事：

1. **输入输出契约**：参数和返回值都有严格类型定义——工具是强类型函数；
2. **谁能用**：每个工具绑定唯一角色（生成世界观只有故事架构师能用，写章节只有章节执行者能用）；
3. **什么技能下能用**：绑定技能上下文（定向重做角色只能在角色设计技能体系下调用）；
4. **运行状态**：任务必须运行中才允许调用；
5. **重试与超时**：创作类长超时、瞬时错误可重试两次；检查类短超时、不重试；
6. **权限级别**：写章节、修订章节、抽取记忆这三类"产生内容"的操作还需协调器审批授权；审计评审不用。

核心是把"谁在什么条件下能干什么"变成**声明式数据**，而不是每个工具内部自己写防御代码。加新工具 = 填一份档案 + 挂一个实现。

**一次调用怎么跑（统一网关流水线）。**

1. **查档案**——工具不存在直接拒绝；
2. **四重授权**——角色、技能、任务状态、审批授权，任何一条不过就拒绝并记录原因；
3. **查重复**——同一任务同一调用意图已执行过就返回上次结果，绝不重复执行；输入对不上也拒绝，防止"同一动作产生两个版本"；
4. **校验输入**——参数不符契约拒绝；
5. **执行**；
6. **校验输出**——返回值不符契约记为失败；
7. **落账**——成功失败都完整记录：谁调的、什么技能、什么输入、什么结果、是否复用旧结果。系统里不存在"不被记录的调用"。

**怎么保证调对工具（五道防线）。**

1. **规划层锁死**：规划阶段模型只能在白名单里选工具，系统校验工具名——模型不知道不存在的东西；
2. **节点层锁死**：每个任务节点构建时声明可用工具，执行器只给节点声明过的那几个，写世界观的节点拿不到"写章节"的入口；
3. **网关授权锁死**：角色 × 技能 × 状态 × 审批四维矩阵，越权即拒；
4. **契约校验锁死**：输入输出强类型校验，坏数据进不了下一环节；
5. **幂等防重锁死**：同一任务同一意图只执行一次，杜绝"调两次产生两版内容打架"。

五道防线叠加的效果：**"调错工具"从"靠模型自觉"变成"结构上不可能"**。模型唯一能走的路就是系统允许的那条，而且每一步都留痕。

一句话总结：**工具是声明式的、调用是网关化的、权限是四维的、执行是幂等的、全程是留痕的**。

## 十九、工具调用技术深挖（追问细节）

### 19.1 九个创作工具

全部以「工具名@版本号」注册，每个工具绑定唯一角色 + 技能 + 访问级别：

| 工具 | 绑定角色 | 绑定技能 | 访问级别 | 备注 |
|---|---|---|---|---|
| `world.generate@1.0.0` | STORY_ARCHITECT | world-building | PROVIDER（调模型） | 生成世界观 |
| `character.generate@1.0.0` | CAST_DESIGNER | cast-network | PROVIDER | 生成角色集 |
| `character.revise@1.0.0` | CAST_DESIGNER | cast-network | PROVIDER | 定向重做角色（target_names） |
| `outline.generate@1.0.0` | OUTLINE_PLANNER | story-architecture | PROVIDER | 生成大纲 |
| `chapter.draft@1.0.0` | CHAPTER_EXECUTOR | chapter-scene | STAGE_WRITE | 生成章节草稿（需协调器审批） |
| `chapter.repair@1.0.0` | CHAPTER_EXECUTOR | targeted-revision | STAGE_WRITE | 定向修订章节（需协调器审批） |
| `memory.extract@1.0.0` | MEMORY_EXTRACTOR | memory-extraction | CANDIDATE_WRITE | 抽取记忆（需协调器审批） |
| `continuity.audit@1.0.0` | CONTINUITY_AUDITOR | continuity-audit | READ | 一致性审计 |
| `quality.evaluate@1.0.0` | QUALITY_REVIEWER | quality-review | READ | 质量评审 |

访问级别设计：**写操作只有两个出口**——章节草稿只进 STAGE_WRITE 暂存区，记忆只进 CANDIDATE_WRITE 候选区；审计评审纯只读。

### 19.2 ToolSpec 声明式设计

每个工具 = 一份 `ToolSpec` 声明 + 一个绑定领域组件的 handler，通过 `ToolRegistry.register` 注册（重复注册报错），`resolve(tool_ref)` 按版本化引用精确查找。

`ToolSpec` 关键字段（全部运行时强制）：

- `tool_id` + `version` → 唯一版本化引用 `tool_ref`；
- `input_model` / `output_model`：Pydantic 输入/输出契约，调用即校验；
- `allowed_roles`：允许的角色集合；`allowed_skill_ids`：允许的技能集合；
- `allowed_run_states`：允许的运行状态（当前仅 RUNNING）；
- `access_level`：PROVIDER / STAGE_WRITE / CANDIDATE_WRITE / READ；
- `timeout_seconds`：创作类 300s，审计评审类 120s；
- `retry_policy`：`max_attempts`，仅对 TRANSIENT 瞬时错误重试（world/character/outline 2 次，章节类 1 次）；
- `idempotent`：全部开启；
- `approval_policy`：`chapter.draft` / `chapter.repair` / `memory.extract` 为 COORDINATOR，其余 NONE；
- `artifact_policy`：STAGE_ONLY / CANDIDATE_ONLY / NONE。

设计价值：权限、重试、幂等、审批、超时等横切关注点从工具实现中抽离成数据，引擎层不认识领域逻辑，只认识注册表。

### 19.3 ToolGateway.invoke 规范调用流水线

1. **输入哈希**：sha256(input.model_dump_json())，参与幂等键；
2. **解析工具**：`resolve(tool_ref)`，未注册 → `DENIED(UNKNOWN_TOOL)`；
3. **影子检查**：shadow 调用直接拒绝（SHADOW_NO_SIDE_EFFECT）；
4. **四维授权**（`_authorization_reason`）：ROLE_DENIED / STATE_DENIED / SKILL_TOOL_DENIED / APPROVAL_REQUIRED；
5. **幂等查询**：以 `(run_id, idempotency_key)` 查内存缓存或 SQLite 预留记录（`reserve_result`）——输入哈希不一致 → IDEMPOTENCY_CONFLICT；执行中 → IDEMPOTENCY_IN_PROGRESS；已完成 → 复用上次结果（trace 标记 `reused=True`）；
6. **输入校验**：input_model 校验失败 → FAILED(SCHEMA_INVALID)；
7. **执行 handler**：异常 → FAILED(HANDLER_FAILED)；
8. **输出校验**：output_model 校验失败 → SCHEMA_INVALID；
9. **结果落账**：生成 `InvocationTrace`（invocation_id / tool_ref / skill_ref / 幂等键 / 输入输出哈希 / outcome / reason / reused / shadow），幂等工具同步持久化 SQLite；返回 `ToolCallResult`。

`workflow_tool_request` 构造类型化信封：`invocation_id = {run_id}:{task_id or planning}:{tool_ref}:{skill_ref}:{input_hash}`，`idempotency_key = {run_id}:{tool_ref}:{skill_ref}:{input_hash}`——幂等键包含输入哈希，断点恢复重放调用时复用原审计行而不冲突。

### 19.4 保证 agent 调用正确工具的五道防线

1. **规划层白名单**：AVAILABLE_PLAN_TOOLS 仅 5 个工具，规划校验强制版本化工具名，模型不知道不存在的工具；
2. **节点级工具白名单**：TaskGraphNode 声明 `tools` 元组，执行器只允许节点调声明过的工具，跨节点调用无入口；
3. **网关四维授权**：角色 × 技能 × 运行状态 × 审批，任何一条不满足 DENIED（`character.revise` 只能角色设计师在 cast-network 下调用；`chapter.draft` 必须持 COORDINATOR 审批）；
4. **输入输出契约校验**：强类型函数，schema 不合规在工具边界被拦，坏数据不进下一节点；
5. **幂等 + 冲突防护**：同一 (run_id, 幂等键) 输入变了 → 冲突拒绝；重复执行 → 返回上次结果；防"同一工具调两次产生两版内容"，保证断点恢复重放无重复副作用。

叠加效果：模型只能走"注册表存在 ∧ 节点声明过 ∧ 权限矩阵放行 ∧ 契约校验通过"的唯一路径，且全程留痕可回溯。

## 二十、Skill 技能体系口头介绍（面试口语版）

> 面试官视角："你的 skill 怎么设计的？和工具调用有什么区别？"——不含代码细节，只讲设计思路。

我先说 skill 是什么。在这个系统里，我刻意把"能力"和"操作"分成两个概念。**skill 是能力的声明**——它描述"系统具备哪项创作能力、这项能力在什么条件下可以用、需要多少资源、干活时用哪套提示词"；**工具是具体的操作**——一次具体的执行动作，有严格的参数和返回值规范。

我把 skill 想成"岗位职责加工作手册"：岗位说明书写清楚这份能力适用于什么任务、需要什么资质、预算多少，工作手册就是配套的提示词模板；工具则是具体的工具本身——电钻就是电钻，有规格、有安全规范、有使用记录。干活时必须两件事同时成立：**人员持证上岗**（被系统指定了正确的技能），并且**用对了工具**（通过了工具的权限检查）。

设计上，每个技能是一份声明式档案，写清楚四组东西：

1. **身份和状态**：技能的名字、版本，以及当前状态——启用、影子（只测试不生效）、禁用、弃用；
2. **适用条件**：能用在什么任务上、什么角色能用、什么题材适用；
3. **资源需求**：需要多少上下文预算、最多调几次工具、最多修复几次、超时多少，以及它能调用哪些工具；
4. **模板**：配套的提示词模板，加载时系统校验模板内容和档案里记录的哈希完全一致，防止"档案和能力脱节"。

选择技能有两条路径。**章节创作这种核心链路，我做成确定性固定管线**：写章节、抽记忆、审计、评审，每个环节固定用对应技能，不搞竞争选择，保证每章走的流程完全一样；**其他任务走竞争式选择器**：系统把任务描述和所有技能逐一比对，先做硬性检查（条件不满足直接出局），再打分，分数必须足够高且明显领先才会被选中，否则宁可暂停等人工处理，也绝不猜。

选中之后还有个关键机制叫"**技能锁定**"：每个任务开始执行时，把选中的技能连同它的版本一起锁定成快照，整个任务期间都用这一版，不会出现"跑到一半技能升级导致行为漂移"。而且这个快照会被完整记录到审计里——事后能精确回答"这次运行用的是哪一版技能和哪一版提示词"。

最后，**技能和工具是双向绑定的**：技能声明自己能用哪些工具，工具声明自己只能在哪些技能下被调用。调用时即便角色对了，技能上下文不对，系统照样拒绝。所以整个设计的逻辑是：**技能决定模型"能不能做这件事"，工具保证"做的时候对不对"**，两层权限叠加，模型行为才真正可控。

一句话总结：**技能管资格、手册和预算，工具管操作、规范和记录；两者双向绑定，构成完整的权限闭环**。

## 二十一、Skill 技能体系技术深挖（追问细节）

### 21.1 Skill 是什么

一个 skill = **一份 JSON 清单（SkillManifest）+ 一个提示词模板**，以 `skill_id@语义化版本`（如 `chapter-scene@1.0.0`）唯一标识。内建技能集固定（`BUILTIN_SKILL_IDS` 强校验，缺一个加载失败）：world-building / cast-network / story-architecture / chapter-scene / targeted-revision / memory-extraction / continuity-audit / quality-review 等，与 9 个工具一一对应绑定。

### 21.2 Manifest 四组设计

**① 身份与状态**：`skill_id`（小写连字符命名正则）+ `version`（严格 semver）；`status`：enabled / shadow（只评估不生效）/ disabled / deprecated；`kind`：primary / audit。

**② 适用条件**：`task_types`、`run_states`、`allowed_roles`、`genre_tags`（题材标签）。

**③ 资源与能力约束**：`compatibility`（输入/输出 schema 版本兼容区间）、`required_context_slices` / `required_artifact_kinds`（上下文切片与产物依赖）、`allowed_tool_ids`（可调用工具集）、`context_budget` / `max_tool_calls` / `max_repairs` / `timeout_budget`（Token/调用/修复/超时四类预算）。

**④ 模板与可审计性**：`prompt_template_path` + `prompt_template_hash`、`audit_for`（作为谁的审计技能）、`manifest_hash`（清单自哈希）。

### 21.3 加载与完整性校验

`load_builtin_catalog`：从 `skill_manifests/*.json` 加载后，**模板文件实际哈希必须与清单声明一致，不一致直接加载失败**；内建技能集必须完整。运行时可用 `set_status` 动态治理（启用/影子/弃用/禁用）。

### 21.4 两种选择模式

**模式 A：章节链路——确定性固定管线（不做竞争）**

`pin_chapter_skills`：固定链 `chapter-scene → memory-extraction → continuity-audit → quality-review`（REPAIR 加 `targeted-revision`）。每章每个门恰好跑一次，**故意不 consult SkillSelector**（固定工作流模式）；但每个技能仍走 `_pin_skill` 校验——status 非 enabled 直接抛错，pin 时 score=100、证据 `governed_chapter`。

**模式 B：规划/通用任务——SkillSelector 竞争式选择**

1. **12 项硬检查**：status、task_type、run_state、actor_role、schema 兼容区间、required_context、required_artifacts、allowed_tools 子集、context_budget、tool_budget、repair_budget、timeout_budget——任一不满足 score=None 出局；
2. **百分制打分**：task_type=40 + run_state=25 + role=15 + schema_context=10 + genre=5 + stable=5（主版本 ≥1 偏好稳定）；
3. **裁决**：主技能必须 **≥80 且领先第二名 ≥10**，否则 `SKILL_AMBIGUOUS` 暂停等人工（绝不猜）；再从 `audit_for` 关联清单选**审计技能**（主技能干活、审计技能交叉验证）。

### 21.5 Pin 机制（版本快照）

`SkillCatalog.pin(run_id, selected)` 生成 `ActiveSkillPin`：run_id + **清单快照 + manifest_hash + template_hash**；`(run_id, skill_id)` 去重，同 run 同技能只 pin 一次。Pin 后所有引用（工具调用、审计、重试）都走 pin——**选的时候是什么版本，用的时候就是什么版本**，防运行中升级导致行为漂移。

### 21.6 与工具 / 节点 / 审计的联动闭环

1. 节点声明 `skills` 元组（TaskGraphNode）；
2. 执行前 pin 声明技能，非 enabled 失败；
3. 工具调用携带 `skill_ref`，网关校验 ∈ 工具 `allowed_skill_ids`，不匹配 → `SKILL_TOOL_DENIED`；
4. 规划审计（planning_audit）记录每次运行使用的技能 pin（skill_ref / manifest_hash / template_hash），事后可精确复现"用的是哪一版提示词"。

### 21.7 Skill vs Tool 区别（技术对照）

| 维度 | Skill | Tool |
|---|---|---|
| 抽象层级 | 能力层（面向任务） | 操作层（面向执行） |
| 本质 | 声明式清单 + 提示词模板 | 强类型函数 + 网关执行 |
| 主要内容 | 适用条件、资源预算、模板哈希 | 输入/输出契约、权限、重试/幂等/审批 |
| 生命周期 | 任务级 pin 一次（每 run 每技能一次） | 每次调用都过网关（per-call） |
| 选择机制 | 固定管线 pin 或选择器竞争打分 | 无"选择"，只有"解析 + 授权" |
| 审计粒度 | 版本快照（template_hash / manifest_hash） | 单次调用（input/output hash + trace） |
| 演进方式 | 升级换提示词模板 | 升级换输入输出契约 |

**双向绑定**：`SkillManifest.allowed_tool_ids`（技能声明能调哪些工具）× `ToolSpec.allowed_skill_ids`（工具声明只能在哪些技能下被调）——角色对但技能不对照样 `SKILL_TOOL_DENIED`。例：`chapter-scene@1.0.0`（写场景能力 + 模板 + 预算）vs `chapter.draft@1.0.0`（写章节操作 + 契约 + 审批 + 幂等）。

**为什么分开**：解耦"选什么能力"与"怎么执行"（技能升级换模板、工具升级换契约，独立演进独立审计）；治理维度不同（技能管宏观授权一次定一次，工具管微观执行每次验一遍）；`allowed_tool_ids` 是集合，支持技能组合多工具，为 N:M 扩展留口子。

**一句话总结**：Skill 决定 agent **能不能做**（资格 + 手册 + 预算），Tool 保证做的时候**对不对**（操作 + 规范 + 记录），双向白名单绑定构成完整权限闭环。

## 二十二、MCP 与技术架构深挖（追问细节）

### 22.1 skills 如何控制工具调用（三层约束）

"skills 控制工具调用"方向正确，但更准确是 **skill 与 tool 互相约束**：

1. **节点声明**：TaskGraphNode.tools 白名单——执行器只允许节点调声明过的工具；
2. **skill 双向绑定**：SkillManifest.allowed_tool_ids（技能声明能调哪些工具）× ToolSpec.allowed_skill_ids（工具声明只能在哪些技能下被调）；
3. **网关校验**：调用请求携带 skill_ref，网关校验 ∈ 工具 allowed_skill_ids，不匹配返回 SKILL_TOOL_DENIED。

### 22.2 有没有用 MCP——没有（查证结论）

- 依赖清单（requirements.txt / pyproject.toml）：requests / gradio / json-repair / pydantic / pytest——无任何 MCP SDK；
- 全库搜索 mcp / modelcontextprotocol / anthropic：零命中；
- 本项目为**自研工具调用架构**：ToolRegistry + ToolGateway（注册/网关）、ToolSpec（契约）、SkillManifest（能力声明）、ProviderTransport（模型层自封装）。

### 22.3 为什么没用 MCP（四个原因）

1. **工具都是进程内函数**：9 个工具调用内部 Python 组件（PlanningGenerator / ChapterGenerator / MemoryExtractor…），无跨进程/跨语言/多客户端需求——MCP 的价值是"标准化暴露工具给外部客户端"，单进程内用不上协议层；
2. **MCP 不提供核心治理语义**：MCP 定义"工具怎么暴露、怎么调用"（传输层 + schema），但不定义权限矩阵、幂等、审批、Token 预算、审计台账——这些是自研网关的灵魂；
3. **零依赖原则**：本地工具 + 零依赖 Web 控制台的形态，引入 MCP SDK 是无收益依赖层；
4. **模型层自封装**：DeepSeek/Gemini 走自研 ProviderTransport（OpenAI 兼容 + 失败分类 + 切换策略），不是通用 LLM 客户端。

### 22.4 自研架构 vs MCP 对照

| 组件 | 本项目实现 | MCP 对应物 |
|---|---|---|
| 工具注册与调用 | ToolRegistry + ToolGateway（进程内） | MCP Server / Client |
| 工具契约 | ToolSpec（输入/输出 Pydantic 模型） | tool schema（JSON Schema） |
| 能力声明 | SkillManifest（JSON + 提示词模板） | MCP prompts / resources |
| 模型接入 | ProviderTransport 自封装 | MCP 不负责模型层 |

### 22.5 接入路径（演进方向）

1. 本系统作为 **MCP Server**：ToolSpec → MCP tool schema（tool_id@version → name，input_model.model_json_schema() → inputSchema），外部 LLM 客户端经 MCP 调用创作工具；
2. **网关放在 MCP 之下**：MCP 管传输，ToolGateway 管治理（授权/幂等/审计照旧）——协议层与治理层解耦；
3. 反向作为 **MCP Client**：需要外部工具（查资料、第三方 API）时接入外部 Server；
4. skills 绑定/选择逻辑依然自研——MCP 不解决"什么能力配什么工具"。

### 22.6 一句话总结

**skills 确实参与控制工具调用（节点白名单 + 双向绑定 + 网关校验三层约束）；本项目没有用 MCP（依赖与代码可证），因为工具是进程内函数、治理语义 MCP 不提供、项目坚持零依赖——MCP 是"工具怎么传输"的协议，本项目解决"工具怎么被治理"，未来跨进程/外部工具接入时把 MCP 作为传输层接在网关之下即可。**
## 二十三、Tools vs Function Calling 深挖（追问细节）

### 23.1 各自定义（不同层次的事物）

- **Function Calling（FC）**：模型 API 能力——请求中声明函数（name + description + 参数 JSON Schema），模型在输出时自主决定调用哪个函数并生成结构化参数 JSON；请求级、无治理；
- **本项目 Tools**：系统架构治理框架——ToolSpec（契约/权限/重试/幂等/审批/预算/超时）+ ToolRegistry + ToolGateway（invoke 流水线）+ 审计台账；持久级、跨运行。

### 23.2 核心区别对照

| 维度 | Function Calling | 本项目 Tools |
|---|---|---|
| 层次 | 模型 API 能力（输出侧） | 系统架构（执行侧 + 治理侧） |
| 解决什么 | 让模型"说出"调什么、参数是什么 | 让调用"被正确执行"：授权/幂等/审计/恢复 |
| 生命周期 | 请求级（一次对话轮次） | 持久级（台账落库、跨运行） |
| 授权 | 无——模型可调任何已声明函数 | 四维授权（角色×技能×状态×审批）+ 节点白名单 |
| 幂等 | 无 | 内容寻址幂等（断点恢复重放不重复） |
| 审计 | 无 | InvocationTrace 全量留痕 |
| 失败处理 | 格式错误客户端自理 | 分类失败 + 重试策略 |
| 调用决策权 | 模型自主选择 | 系统编排调用（workflow_tool_request 由代码构造） |

### 23.3 最本质区别：调用决策权

FC 为"模型自主 agent 循环"设计（模型每步自己选函数）；本项目是 Plan-and-Execute——路径由规划器决定，节点执行器按流程代码调用工具，模型的输出（草稿/评审报告）是工具的结果而非调用决策。**调用决策权在编排层，不在模型手里**——FC 的适用场景与项目的编排模型不匹配。

### 23.4 为什么不用 Function Calling（五个原因）

1. **FC 只是"入口"不是"治理"**：不提供授权/幂等/审批/审计/恢复——项目工具层的全部价值在治理，用 FC 只是换入口，治理仍要全自研；
2. **FC 授权模型冲突**："声明了就能调"，权限靠调用方自行过滤声明；项目需要四维精细化授权（评审员才能调 quality.evaluate、章节工具需协调器审批），FC 表达不了；
3. **长任务恢复**：FC 请求级无状态；项目需要调用可重放、可查账（幂等键 + 审计台账）；
4. **多模型无感**：各家 FC 格式有差异；"提示词 JSON + 契约 + 解析阶梯"对模型实现无感，换模型零成本；
5. **哲学冲突**：FC 鼓励模型每步自由选函数，与"系统编排下的受控调用"相悖（ReAct 式漂移风险）。

### 23.5 诚实补充：FC 的等价物与适用场景

- FC 核心价值（模型输出结构化参数）由"提示词只输出 JSON + Pydantic 契约（extra=forbid）+ 四级解析阶梯"等价实现，解析失败率被修复阶梯压到极低；
- 何时才需要 FC：做"模型自主决策的对话式 agent"（模型自己决定下一步调什么、多轮工具反馈）时，FC 的原生结构化输出能减少解析成本；
- 两者不冲突：FC 可只作为"模型输出层"增强接入，网关治理层照旧——FC 解决"输出结构化"，Tools 解决"调用被治理"。

### 23.6 一句话总结

**Function Calling 是"让模型说出调用意图"的 API 能力（模型自主选、请求级、无治理）；本项目的 tools 是"让调用被正确执行"的系统架构（系统编排、持久级、四维授权 + 幂等 + 审计 + 恢复）——不用 FC 是因为调用决策权在编排层、治理能力 FC 不提供、多模型无感与长任务恢复需求，FC 的核心价值已由"提示词 JSON + 契约 + 四级解析阶梯"等价实现；未来做模型自主 agent 时可把 FC 作为输出层增强接在网关之下。**
## 二十四、质量门控口头介绍（面试口语版）

> 面试官视角："你的质量门控怎么做的？六维度评审是什么？不通过怎么修订？怎么保证评审可靠？"——不含代码细节，只讲设计思路。

我的质量门控核心思路：一章写完不能直接定稿，必须过"**客观规则 + 主观评审**"双道闸，两道都过才算数。

**先说"客观规则"这道闸**，它不走模型，是纯代码计算：第一是篇幅——章节实际中文字数和目标字数必须在一个合理区间内，太短说明没写到位，太长说明注水；第二是角色出场——这一章该出场的角色，正文里必须真的出现。这两条是硬指标，模型说写得再好也不影响它。

**再说过"主观评审"这道闸**：我让一个独立的评审模型给章节在六个维度打分，每维一到五分：

1. 文风跟全书一不一致；
2. 角色言行符不符合人设；
3. 文笔流不流畅；
4. 场景和情节完不完整；
5. 对话自不自然；
6. 内容有没有覆盖大纲要求的情节节点。

打分的同时每个维度必须附一句理由。关键设计：**评审模型和写作模型是分开的，甚至可以是不同的模型**——写的人不能给自己打分，避免自我评审偏见；评审调用还会用更低一点的温度，让评分更稳定。两道闸都过才算通过：任何一个维度低于底线、平均分不够、篇幅越界、或大纲要求的情节没写到，都算不通过。

**不通过怎么办？** 我的原则是"**带着诊断书定向修复**"，不是整章重写：

1. 系统把失败的具体原因整理成一份**修复简报**——告诉模型"是篇幅不够、还是对话自然度只有两分、还是某个情节节点没写到"，模型知道错在哪，而不是笼统地重写；
2. 修复走专门的**定向修订流程**，只针对失败段落做局部重写，原来的版本保留下来，可对比、可回退；
3. **修复有次数上限**：同一章最多修两次，两次还不达标就停下来转人工处理——宁可让人看，也不无限循环烧成本。

**最后说怎么保证评审系统本身可靠**，我靠五件事：

1. **双引擎**：主观质量让模型评，客观指标让代码算，两者互补——模型再能说会道也骗不过硬指标；
2. **独立裁判**：评审模型和写作模型分离，不自己给自己打分；
3. **硬伤前置**：明显的硬伤（章节身份对不上、正文为空、与前面设定硬冲突）根本不进评审环节，直接拦下转人工，不浪费评审成本；
4. **宁缺毋滥**：评审模型自己出错（输出格式坏、调用失败）时，系统不会随便给个分数放行，而是标记评审失败、暂停处理——**绝不让"无法评审"变成"默认通过"**；
5. **全程留痕**：每次评审用的模型、提示词版本、分数、被拒原因全部记录，事后可复现当时判定。

一句话总结：**质量门控 = 客观规则兜底 + 独立模型主观评审 + 失败带诊断书定向修复 + 修复限次转人工 + 评审失败宁停不放水**。

## 二十五、质量门控技术深挖（追问细节）

### 25.1 六维度评审 + 规则指标

评审器（`EvaluatorReport`）按 6 维度打分，每维 1-5 分 + 一句理由：

| 维度 | 评审内容 |
|---|---|
| 文风一致性（style_consistency） | 与全书已确立的文风、叙述视角是否一致 |
| 角色一致性（character_consistency） | 人物言行是否符合人设，有无 OOC |
| 文笔流畅度（prose_fluency） | 语句是否通顺、有无生硬表达 |
| 场景完整度（scene_completeness） | 本章场景描写、情节推进是否完整 |
| 对话自然度（dialogue_naturalness） | 对话是否符合角色口吻、是否自然 |
| 内容对齐度（content_alignment） | 是否覆盖大纲要求的剧情节点 |

规则指标（`CharCountMetricsEvaluator`，确定性、不走模型）：

- **篇幅比例**：中文字符数 / 目标字数 ∈ [0.80, 1.25]（`QualityPolicy` 默认阈值）——太短或注水都判失败；
- **角色提及**：正文是否实际出现应出场角色的名字/别名。

### 25.2 评审判定流程（`ProjectScopedEvaluationAdapter.review`）

1. **硬失败前置**：project_mismatch / empty_body / chapter_identity_mismatch（plan_id、chapter_plan_id、章节号对不上）/ continuity_hard_conflict → **直接 PAUSE，连评审调用都不发**；
2. **规则指标测量**：篇幅比例、角色提及（确定性计算）；
3. **LLM 六维评审**：独立评审模型按 1-5 分输出 JSON，`EvaluatorReport` 契约校验（每维必填 reason、分数 int 1-5），解析失败最多重试 `maximum_evaluator_attempts=2` 次；
4. **阈值判定**：任一维度 < 3 → `dimension_below_minimum`；平均分 < 3.5 → `mean_below_minimum`；篇幅越界 → `length_ratio`；required_beats − located_beats 非空 → `missing_plan_beat`；
5. **决策出口**：无失败 → ACCEPT；有失败且修复未超限 → REPAIR（reason_codes 携带**具体失败项**）；修复耗尽 → PAUSE(`repair_budget_exhausted`)；评审器出错 → EVALUATOR_ERROR。

### 25.3 针对性修订机制（带诊断书的定向修复）

1. **失败项即引导信号**：REPAIR 决策的 `reason_codes` 精确到失败维度（如 `length_ratio`、对话维度分不足）；
2. **修复简报**：`repair_brief` 打包 failure_codes + 旧草稿证据（artifact_id / revision / evidence_sha256）+ 上下文摘要——修订请求自带"原稿证据 + 失败清单"；
3. **定向修订工具**：下一轮生成改走 `chapter.repair@1.0.0`（绑定 targeted-revision 技能），只针对失败段落局部重写，不整章推倒；
4. **版本留痕**：新版本作为新 revision 提交，旧版本保留可对比、可回退；
5. **修复预算硬上限**：`maximum_repairs=2`，第 3 次仍不达标 → PAUSE 转人工，杜绝无限低质量循环烧 token；每次修复的 `repair_attempt` 带入下一次评审请求。

### 25.4 评审系统可靠性六道保障

1. **双引擎互补**：主观质量靠 LLM 六维评审，客观指标靠确定性规则——模型"说写得好"但字数只有一半照样过不了门；
2. **独立裁判模式**：writer 与 judge 使用**不同模型**（代码注释明确），避免自我评审偏差；
3. **低温评审**：评审调用 temperature=0.2，评分稳定性高于创作调用；
4. **硬失败前置 + 契约校验**：身份错位/空正文/硬冲突不进评审；评审输出过 Pydantic 严格契约，解析失败重试 2 次后降级 `EVALUATOR_ERROR` 暂停——**绝不伪造分数放行**（"never to a fabricated score"）；
5. **全链路审计**：评审调用记录 prompt_sha256 / response_sha256 / 模型名 / 失败原因，报告关联 artifact revision——事后可复现判定；
6. **策略参数化 + 版本化**：所有阈值集中在 `QualityPolicy`（POLICY_VERSION 1.0.0），调参不动代码；决策、修复轮次全部落库，为调策略提供数据依据。

**一句话总结**：确定性规则 + 独立模型裁判 + 硬失败前置 + 阈值策略化 + 修复预算封顶——主观质量让独立模型评，客观指标让代码算，评审失败降级暂停而非放水，修订失败限次转人工，每一步留痕可复现。

## 二十六、提示词工程口头介绍（面试口语版）

> 面试官视角："提示词工程方面，你这个项目的提示词是怎么写的？如何通过提示词约束大模型输出的？"——不含代码细节，只讲设计思路。

我的提示词工程核心思想：**按任务性质分四类提示词，每类用不同的写法；约束输出靠"提示词软约束 + 工程硬约束"四层体系，而不是只靠提示词**。

**先说四类提示词**，同一套系统里有四种完全不同的任务：

1. **规划提示词**（任务拆解）——"封闭式"写法：告诉模型只能用哪几个工具、每个步骤必须声明哪些字段、先后顺序有什么规则，最后强制只输出 JSON，温度压得很低；
2. **创作提示词**（写小说正文）——"开放式"写法：核心是**角色扮演**——设定一个顶级作家的身份锚定文风；然后给风格基调、正反示例（"不要写'她很尴尬'，要写'她耳根一闪而过的绯红'"）；再给两篇范文学风格但明确禁止参考范文里的角色和情节；最后用**变量插槽**把世界观、角色档案、前文情节、本章大纲全部注入——**把信息喂全了，模型就没有胡编的空间**；
3. **评审提示词**（六维打分）——每维给 1-5 分加一句理由，强制只输出 JSON，温度 0.2；
4. **修复提示词**（修复坏 JSON）——把期望的 JSON Schema 直接发给模型让它照着修，温度 0，禁止任何解释。

**再讲怎么约束输出，我靠四层，提示词只是第一层：**

1. **提示词内约束**：角色锚定风格、禁止项、输出格式指令——靠模型自觉，会漂移；
2. **结构化输出**：所有程序要消费的输出强制"只输出 JSON"，用严格类型契约解析——多一个字段、少一个字段都判失败；
3. **四级解析阶梯**（最关键的工程手段）：模型输出先严格解析 → 失败用 JSON 修复库做有界修复再试 → 再失败把期望 schema 发给模型修一次 → 还失败返回类型化失败——**绝不猜测、绝不放行坏数据**；"模型到底输出了什么"原始内容全程留痕，能观测每次是怎么解析出来的；
4. **流程兜底**：格式问题靠契约校验，内容写错靠连续性审计，写得不好靠质量门控，瞎编靠记忆系统注入准确上下文——**提示词管不住的事情，由系统流程管**。

**工程管理上**：提示词全部版本化（正文生成提示词迭代了六版），与代码解耦放在独立文件里，每次调用记录提示词版本哈希，事后能精确复现"哪版提示词产出了什么"。

一句话总结：**创作任务用角色扮演和示例给自由度，规划评审任务用白名单和 JSON schema 收确定性；约束输出靠"软提示词 + 硬契约 + 四级解析阶梯 + 流程兜底"四层体系，坏输出在结构上就进不了系统。**

## 二十七、提示词工程技术深挖（追问细节）

### 27.1 四类提示词对照

| 类型 | 代表 | 写法核心 | 温度 |
|---|---|---|---|
| 规划提示词 | `_PLAN_PROMPT`（规划器） | 工具白名单 + 步骤字段约束 + 依赖规则 + 只输出 JSON | 0.3 |
| 创作提示词 | `prompt/generate_prompt/prompt_v6.txt`（章节生成） | 角色扮演锚定文风 + 正反示例 + 变量插槽 | 高（创作自由度） |
| 评审提示词 | `_EVALUATION_PROMPT`（六维评审） | 维度定义 + 严格评分指令 + 每维必附理由 + 只输出 JSON | 0.2 |
| 修复提示词 | `_REPAIR_PROMPT`（schema 修复） | 期望 JSON Schema + 修复指令 + 禁止解释 | 0.0 |

原则：**任务越需要确定性，提示词越"封闭"（白名单、schema、禁止项）；越需要创造性，越"开放"（角色、风格、示例）**。温度随确定性需求梯度变化（0.0 → 0.3 → 0.2 → 创作高温）。

### 27.2 创作提示词六部分结构（prompt_v6，10.5KB，迭代至第 6 版）

1. **角色扮演与核心指令**：立身份（"你是顶级日常系轻小说作家'夏目温人'"）——用角色锚定文风，比直接说"写得温馨"有效得多；
2. **风格基调与创作哲学**：定义氛围边界 + 正反对比（"不是写'他们吵架了'，而是写'杯子放下的声音比平时重了一点'"；"杜绝一切强烈的、戏剧化的情感爆发"）；
3. **具体写作技巧指令**：四组细化（叙事视角/细节描摹/对话风格/情感表达），每条带 Show-Don't-Tell 正反例；
4. **风格范例学习（Few-Shot）**：两篇完整范文 + 明确警告"禁止参考示例中的角色和情节"——给风格不给素材，防抄袭示例剧情；
5. **创作任务（变量插槽）**：`{world}` 世界观 / `{characters}` 出场角色 / `{last_passage}` 上一章 / `{history}` 前文情节 / `{this_passage_request}` 本章大纲 / `{is_NPC}` 是否允许临时角色 / `{words}` 字数 / `{styles}` 参考文风——**"给全信息"本身就是约束，上下文喂够模型才不需要胡编**；
6. **最终检查与提醒**：收尾重申最关键的 2-3 条硬约束，防长提示词"尾部遗忘"。

### 27.3 四层约束体系

**第一层：提示词内软约束**——角色/禁止项/格式指令，靠模型自觉，会漂移。

**第二层：结构化输出硬约束**——程序消费的输出强制"只输出 JSON，不要任何其他文字、不要 markdown 代码块标记"；输出 schema 预定义（PlanStep / EvaluatorReport），Pydantic 契约（`extra="forbid"`）解析，多字段即失败。

**第三层：四级解析阶梯**（`StructuredCreativeAdapter._parse`）：

1. 严格解析：`contract_type.model_validate_json(raw)`，成功即用（parse_route=STRICT_JSON）；
2. json_repair 有界修复后再试（JSON_REPAIR）——处理漏括号/多逗号类小错；
3. 模型定向修复：把**期望 JSON Schema** 连同坏文本发给模型（`_REPAIR_PROMPT`，T=0.0，"不要输出任何解释"），再过契约（SCHEMA_REPAIR）；
4. 类型化失败：返回 `SchemaFailure`，**绝不猜测、绝不静默放行**。

每级有限制：json_repair 有界、模型修复只发一次。原始输出以 `RawCreativeArtifact` 保留（含 sha256）——"模型到底输出了什么"全程留痕，parse_route 标记解析路径，可观测。

**第四层：流程层兜底**——契约校验管格式；连续性审计管"写错了"；质量门控管"写不好"；记忆系统管"瞎编"（注入准确上下文，模型没有编造空间）。

### 27.4 工程化管理

1. **版本化迭代**：正文生成提示词 v1→v6 六版文件共存，演进可追溯，可关联分析"哪版提示词产出什么质量"；
2. **模板与代码解耦**：提示词放独立文件（`prompt/` 目录、skill manifest `prompt_template_path`），代码只引用路径；技能模板 `template_hash` 与清单声明一致才加载（完整性校验）；
3. **全链路审计**：每次调用记录 `prompt_sha256`（提示词版本指纹），可精确复现；
4. **按任务定制温度**：修复 0.0 / 规划 0.3 / 评审 0.2 / 创作高温——同一模型按任务分配确定性预算。

### 27.5 一句话总结

**提示词层面：用角色扮演锚定风格、用正反示例约束行为、用变量插槽喂全信息、用"只输出 JSON"锁定结构；工程层面：四级解析阶梯保证坏输出进不了系统，契约校验 + 审计 + 门控把"格式、正确性、质量"三道关全部变成系统行为，而不是模型的自觉。**

## 二十八、存储选型口头介绍（SQLite 与向量库）（面试口语版）

> 面试官视角："SQLite 是干嘛用的？为什么用它存结果和记忆？为什么不用向量数据库？"——不含代码细节，只讲设计思路。

我的回答分三部分：SQLite 存什么、为什么选它、为什么不用向量库。

**先讲 SQLite 存什么。** 在这个系统里，SQLite 是唯一的"事实源"——所有要持久化的东西都进这一个库：创作资产（世界观、角色、大纲、章节正文，带版本号）、记忆（候选区和正式区的分层事实）、运行状态（任务状态、运行事件流）、审计记录（每次模型调用、每次工具调用）、以及修订版本链。

**为什么选 SQLite，四个原因：**

1. **事务原子性**：系统最核心的写入模式是"产物、状态、事件"在同一个事务里原子提交——要么全成功要么全回滚。这是断点恢复的前提：不会有写到一半的脏状态。SQLite 提供完整 ACID 事务；
2. **零部署**：本地单进程工具，SQLite 是 Python 内置，不需要装数据库服务器——上 MySQL 是给这个场景背一个巨大的运维负担；
3. **并发模型匹配**：系统是单写者串行调度，正好是 SQLite 的舒适区；
4. **查询能力够用**：记忆检索用全文索引做关键词相关性，冲突检测、去重、幂等全是结构化 SQL——一个库全搞定。

**为什么不选其他方案？** JSON 文件没有事务和查询能力；纯内存一挂全丢，跨运行复用资产就没了；MySQL 是过度设计；Redis 是内存型不持久；向量数据库——重点讲。

**为什么不用向量数据库，核心是三个字：不匹配。**

1. **检索模型不匹配**：我的记忆是结构化事实，检索时我知道确切要找什么——角色名、情节节点，需要精确命中；向量库给的是语义近似匹配，是"大概意思"的模糊检索。给精确查询套一层近似，反而引入不确定性；
2. **精确性要求**：记忆系统最核心的两个操作——冲突检测（查同一主体同一属性下有没有矛盾事实）和去重——都要求 100% 命中，靠的是精确匹配和哈希。向量检索是概率召回，可能漏——漏一条冲突，冲突检测就失效，这是拆自己的地基；
3. **规模不匹配**：一本书的事实是几千到几万条，SQL 加索引毫秒级返回；向量库是给百万级高并发场景设计的，杀鸡用牛刀；
4. **成本**：用向量库意味着每次写入要调 embedding 模型——多一层 API 调用、Token 成本和延迟，引入外部依赖；embedding 模型更新还会导致向量分布漂移，旧向量全失效要重算。

但要诚实说边界：如果未来记忆从结构化事实变成开放文本（比如整段剧情摘要、玩家对话历史），或者做跨作品百万级知识库，语义检索才有价值，我会引入向量库——而且演进路径是 SQLite 生态的向量扩展，**可以原地升级，不用推倒重来**。

一句话总结：**SQLite 提供"事务、零部署、精确查询"这组恰好匹配项目需求的组合；向量库是给"近似检索、大规模、开放文本"准备的——我的记忆系统要的是确定性，不是相似性。**

## 二十九、存储选型技术深挖（追问细节）

### 29.1 SQLite 存储内容（五类）

| 数据类别 | 具体内容 | 支持的系统能力 |
|---|---|---|
| 创作资产（artifacts） | 世界观、角色集、大纲、章节正文，含 revision、status、raw_bytes、sha256 | 版本管理、验收状态、证据溯源 |
| 记忆 | memory_candidates（M0 候选）+ memory_records（M1-M3 正式记忆）+ memory_fts（全文索引） | 分层记忆、证据链、检索注入 |
| 运行状态 | runs / tasks / run_events（事件流）/ run_leases（租约 + fencing token） | 状态机、断点恢复、暂停/取消 |
| 审计 | 工具调用台账（invocation/result）、规划审计清单（audit_manifests，含 prompt/response sha256） | 全链路可追溯 |
| 修订链 | revisions、supersedes_id 版本链 | 定向修订、回退 |

### 29.2 为什么选 SQLite（六个原因）

1. **事务原子性**：核心写入模式是"产物 + 状态 + 事件"同一事务提交（`write_transaction` 封装），ACID 保证断点恢复无半写状态；
2. **单文件零部署**：Python 内置模块，无需数据库服务器，匹配本地单进程工具形态；
3. **并发模型匹配**：本地运行调度器单写者串行执行，落在 SQLite 单写者优势区间；多进程并发写才考虑 PostgreSQL；
4. **结构化查询 + 全文检索**：记忆检索走 `memory_fts`（FTS top-k），冲突检测/候选去重/幂等查询走结构化 SQL（如 `NOT EXISTS(successor.supersedes_id = current.memory_id)`）；
5. **内容寻址友好**：BLOB + sha256 字段 + 唯一约束做内容寻址去重（`ON CONFLICT DO NOTHING`），JSON 文件做不到原子去重；
6. **可迁移/可备份/可导出**：`migrations/` 版本化迁移；单文件备份；`export.py` 导出 `worlds/`、`characters/`、`novel/` 目录文本——数据库不是牢笼。

### 29.3 其他方案对比

| 方案 | 为什么不选 |
|---|---|
| JSON/文件系统 | 无事务（写一半断电即损坏）、无查询能力、多文件原子更新不可能 |
| 纯内存 | 进程一挂全丢；跨运行复用资产无法实现 |
| MySQL/PostgreSQL | 需独立服务、运维成本高；单写者场景 SQLite 性能足够，过度设计 |
| Redis | 内存型，持久化非强项；无分布式/缓存诉求 |
| 向量数据库 | 见 20.4 |

### 29.4 为什么不用向量数据库（五个原因 + 边界）

1. **检索模型不匹配**：记忆是事实三元组（subject/predicate/value），检索键是明确的实体名/剧情节点——需要结构化等值查询 + 关键词检索，不是语义相似度 top-k；向量检索给精确查询套近似匹配，引入不确定性；
2. **精确性要求**：冲突检测（同主体同谓词查当前有效记录并比对 value）必须 100% 命中，漏一条就漏一个冲突；候选去重靠 `normalized_fact_hash` 哈希精确匹配——两者都是确定性匹配，向量是概率召回，**把地基换成近似检索等于拆掉可靠性**；
3. **量级不匹配**：单本书事实量级几千~几万条，SQLite + 索引 + FTS5（BM25）毫秒级返回；向量库为百万级高并发分布式设计，杀鸡用牛刀；
4. **embedding 成本**：每次记忆写入多一次 embedding 调用（API 成本 + 延迟）；引入外部服务依赖，违背零部署形态；
5. **embedding 漂移**：embedding 模型更新导致向量分布变化，旧向量失效需全量重算——模型侧不确定性传导到存储层。

**边界（何时才需要向量库）**：
- 记忆从结构化事实变成开放文本（整段剧情摘要、玩家对话历史、非结构化叙事）——无固定 subject/predicate 可查，只能语义召回；
- 跨作品/跨用户百万级知识库 + 多租户并发检索；
- 游戏动态叙事场景（玩家行为历史是开放文本 + 状态向量）。

**演进路径**：SQLite 生态的 `sqlite-vec` 扩展可在不引入独立服务前提下给 FTS 加向量能力——**先精确后语义，需要时原地升级**。

### 29.5 一句话总结

**SQLite 提供"事务、零部署、精确查询"这组恰好匹配项目需求的组合；向量库是给"近似检索、大规模、开放文本"准备的。记忆系统的冲突检测与去重建立在确定性匹配之上，换成近似检索等于拆地基；未来出现开放文本记忆或大规模检索需求时，通过 sqlite-vec 原地升级。**

## 三十、短长期记忆口头介绍（面试口语版）

> 面试官视角："记忆系统如何处理短期记忆和长期记忆的？"——不含代码细节，只讲设计思路。

核心结论：**这套系统里短期/长期不是两个分开的存储，而是同一个分层记忆体系里的生命周期维度——短期是"使用态"，长期是"存储态"，中间靠"验收巩固"转化。**

**先说短期记忆，它有三种形态：**

1. **工作记忆**——单次运行内的临时状态，比如正在生成的章节上下文，运行一结束就回收、不持久化，相当于人脑的"当前意识"；
2. **即时上下文**——每次写新章节前，系统从长期记忆里按需捞出来的那批相关事实，组装成带 Token 上限的上下文包，用完即弃，相当于"注意力工作区"；
3. **短期缓冲**——每章刚抽取出来的事实候选，在章节验收之前停留在隔离区、不参与任何生成，相当于"海马体临时缓冲"。

**再说短期怎么变成长期——记忆巩固，这是最核心的设计。** 短期记忆不会自动变长期，必须经过巩固：

```
生成章节 → 抽取事实进短期缓冲 → 连续性审计 + 质量评审 → 章节验收定稿 → 候选提升为正式记忆（长期）
```

两个关键点：

1. **验收即巩固**——没定稿的章节，它的记忆永远停在缓冲里，之后被新内容冲走，相当于被遗忘；
2. **巩固前有质检**——候选转正之前要过冲突检测和策略裁决，**不是所有短期内容都配成为长期记忆**。这模仿了人脑：不是所有经历都能进长期记忆。

**再说长期记忆怎么读——永远经过短期装载。** 长期记忆从不直接喂给模型。每次生成前，系统以本章剧情节点为查询键，从长期库里检索相关事实，组装成带预算的上下文包注入。**长期存储可以很大，每次使用必须小且准**——这就是"长期负责记得住、短期负责用得好"的分离。

**最后说遗忘，分四级：**

1. 工作记忆：运行结束**主动回收**；
2. 即时上下文：**用完即弃**，下次重新组装；
3. 短期缓冲：未验收的候选被新内容**冲走**（被动淘汰）；
4. 长期记忆：**"有效遗忘"**——新事实取代旧事实后，旧版本退出检索（模型层面忘了），但物理保留用于审计和回退。

长期层的原则：**宁可多存，不可错删。**

**和业界方案对比定位：** 滑动窗口只留最近几轮，长文必忘；摘要压缩有损不可逆；RAG 语义近似召回，精确事实检索不稳。本项目走 MemGPT 式分层——上下文窗口当短期、外部持久库当长期、检索装载衔接——但多加了一层：**可信度分层和验收门控**，决定"什么内容配进入长期记忆"。比单纯分层更接近人脑。

一句话总结：**短期三种形态管"用"，长期正式事实管"存"，验收巩固管"转化"，四级遗忘管"淘汰"——整个设计模仿人脑的"经历→巩固→长期化"过程，同时每一步可追溯。**

## 三十一、短长期记忆技术深挖（追问细节）

### 31.1 核心结论：短期/长期是生命周期维度，不是两个存储

同一个 M0-M5 分层同时承载两个维度：

- **生命周期维度**：短期 = 使用态（M5 工作层 / M4 检索组装 / M0 候选缓冲）；长期 = 存储态（M1-M3 正式记忆）；
- **可信度维度**：候选（M0）vs 正式（M1-M3）——短期缓冲有可信度过滤，不是所有短期内容都能转长期。

### 31.2 短期记忆三种形态

| 形态 | 对应层 | 生命周期 | 内容 | 人脑类比 |
|---|---|---|---|---|
| 工作记忆 | M5 工作层 | 单次运行内 | 当前任务上下文快照、正在生成的草稿状态 | 当前意识 |
| 即时上下文 | M4 检索层 | 每次生成前临时组装 | 从长期记忆按需检索的 ContextPack（max_tokens 预算） | 注意力工作区 |
| 短期缓冲 | M0 候选层 | 本章内 | 本章抽取的事实候选，验收前隔离、不参与生成 | 海马体临时缓冲 |

### 31.3 短期→长期：验收巩固机制（核心设计）

```
生成章节 → 抽取事实进 M0（短期缓冲）
  → 连续性审计 + 质量评审（巩固过程中的校验）
  → 章节验收通过 → M0 候选提升为 M1/M2/M3 正式记忆（长期存储）
```

三个关键点：

1. **验收即巩固**：只有章节验收定稿，候选才提升为长期记忆（对应人脑"睡眠巩固"）；未定稿章节的记忆永远停在短期缓冲，不参与检索 ≈ 被遗忘；
2. **巩固前有质检**：候选转正前过冲突检测（同主体同谓词比对）+ 策略层裁决（`decide_promotion`：PROMOTED / REVIEW_REQUIRED / CONFLICTED）——不是所有短期内容都值得转正；
3. **提升后证据保留**：长期记忆锚定来源产物（artifact revision + span + sha256），转正不是变成孤立文本，而是带证据链的正式事实。

### 31.4 长期记忆读取：永远经过"短期装载"

M1-M3 从不直接喂给模型，读取永远走 M4：

```
写第 N 章前 → 以本章剧情节点为查询键 → 从 M1-M3 检索相关事实
  → 组装成带 Token 预算的 ContextPack → 注入模型
```

长期存储可以很大，每次使用必须小且准——长期负责"记得住"，短期负责"用得好"，两者解耦（也是记忆膨胀问题的解法基础）。

### 31.5 遗忘策略：四级

| 层 | 遗忘机制 |
|---|---|
| M5 工作层 | 主动回收：运行结束即清空，不残留 |
| M4 检索层 | 自然消亡：每次用完即弃，下次重新组装 |
| M0 候选层 | 被动淘汰：未验收候选停留隔离区、不参与检索，被新内容"冲走" |
| M1-M3 长期层 | 有效遗忘：supersedes 版本链——被取代旧记录退出检索（模型层遗忘），物理保留（审计层可追溯） |

长期层设计哲学：**"有效遗忘"不是删除而是降级**——宁可多存，不可错删。

### 31.6 与业界方案对比

| 方案 | 做法 | 局限 |
|---|---|---|
| 滑动窗口 | 只保留最近 N 轮 | 长文必忘前文——最粗 |
| 摘要压缩 | 历史压缩成摘要 | 摘要有损，细节丢失不可逆 |
| RAG 检索 | 外部库 + embedding 检索 | 语义近似召回，精确事实检索不稳 |
| MemGPT 式分层（本项目基础） | 上下文窗口（短期）+ 外部持久存储（长期）+ 检索装载 | —— |
| 本项目特色 | 叠加"可信度维度"：短期缓冲有候选/正式之分，巩固有验收门控 | 更接近人脑：不是所有短期经历都能成长期记忆 |

定位：**生命周期分层（短期工作集 / 长期存储）+ 可信度分层（候选 / 正式）+ 验收巩固门控**。

### 31.7 一句话总结

**短期三种形态管"用"（工作层 / 检索层 / 候选层），长期 M1-M3 管"存"，验收巩固管"转化"，四级遗忘管"淘汰"——模仿人脑"经历→巩固→长期化"过程，同时每一步可追溯。**

## 三十二、MemGPT 参考口头介绍（面试口语版）

> 面试官视角："你说整体参考了 MemGPT，你能介绍一下这个 MemGPT 吗？你项目参考了它哪些内容，跟它做的区别在哪？"——不含代码细节，只讲设计思路。

**先介绍 MemGPT。** MemGPT 是 2023 年 UC Berkeley 的一篇论文，核心思想是一个惊人的类比：**把大模型当成操作系统，把上下文窗口当成主内存（RAM），把外部存储当成磁盘**。它解决什么问题？上下文窗口又小又有限，而历史、知识是无限的。传统做法要么全塞进窗口导致爆窗，要么只留最近几轮导致遗忘。MemGPT 的方案是**虚拟内存管理**：让 agent 像操作系统分页一样，在上下文和外部存储之间主动搬运数据——上下文快满了就"换出"到归档存储，需要旧知识就"换入"到上下文。

具体架构是**两层内存**：主上下文（核心记忆 + 当前对话，永远在上下文里）和外部上下文（归档记忆存长期事实，回忆记忆存完整历史）。配套三个机制：

1. **模型自我编辑记忆**：模型通过函数调用自己管理记忆——自己决定写什么、改什么、删什么；
2. **记忆压力机制**：上下文快满时触发模型做"换出"决策；
3. **检索换入**：需要旧信息时模型自己搜归档库并加载进上下文。

**我参考了它什么？三处：**

1. **分层记忆的总体架构**——上下文管短期、外部存储管长期、按需检索装载衔接。我的检索层"换入"和工作层就是它概念的工程化；
2. **"记忆需要主动管理而非被动塞满"**这个判断——不能赌模型记得住，记忆管理必须变成显式机制；
3. **核心设定常驻、细节按需加载**的思路——角色档案/世界观这类核心事实始终可检索，细节按需捞取。

**但跟它的区别，关键在于"信任模型"完全相反。** 四个最本质的区别：

1. **记忆写入权**：MemGPT 是模型自己编辑记忆——模型说记住就记住、说删就删，写入无门控，所以有幻觉记忆和污染风险；我的系统里**模型只能"提议"，系统负责"裁决"**——抽取出来的先进候选隔离区，过证据校验、冲突检测、审计、验收门控、策略裁决，验收才转正。一句话：**它信任模型，我信任系统**；
2. **记忆单元**：MemGPT 存任意文本块和对话历史；我存**结构化事实三元组**，每条绑定字节级证据——哪一章哪段原文，来源可验证、不可伪造；
3. **检索方式**：MemGPT 用向量语义检索（"大概意思"的模糊匹配）；我用**结构化精确检索 + 关键词全文索引**——因为我的检索键是明确的角色名和情节节点，需要精确命中；
4. **遗忘机制**：MemGPT 靠记忆压力触发**模型自觉**换出（模型决定忘什么）；我用**确定性机制**——验收巩固决定什么进长期，版本取代链决定什么退出检索，遗忘是系统决策不是模型自觉。

一句话总结：**MemGPT 提供了"上下文当内存、存储当磁盘、按需换入换出"的分层记忆思想——这是架构灵感；但本项目把它改成"模型提议、系统裁决"，把文本块改成带证据的事实三元组，把语义检索改成精确检索，加了它没有的可信度分层和验收门控——借鉴了它的"形"，替换了它的"魂"。**

## 三十三、MemGPT 参考技术深挖（追问细节）

### 33.1 MemGPT 是什么

- 论文：《MemGPT: Towards LLMs as Operating Systems》（UC Berkeley，2023，arXiv:2310.08560），后商业化改名为 **Letta**；
- 核心类比：LLM = 操作系统，上下文窗口 = 主内存（RAM），外部存储 = 磁盘——解决"上下文有限 vs 知识无限"的矛盾；
- 两层内存层次：

| MemGPT 层级 | 内容 | 特点 |
|---|---|---|
| 主上下文（in-context） | 核心记忆（人设 + 系统指令，永远在）+ 工作上下文（当前对话） | 小、快、易失 |
| 外部上下文（external） | 归档记忆（长期事实/事件，向量库存）+ 回忆记忆（完整对话历史日志） | 大、持久、按需加载 |

- 三大机制：
  1. **自我编辑记忆**：模型调函数管理记忆（core_memory_append/replace、archival_memory_insert/search、conversation_search）——写入/删除由模型决策；
  2. **记忆压力**：上下文接近上限时触发模型"换出"决策；
  3. **检索换入**：需要旧信息时模型自行检索归档库加载进上下文。

### 33.2 项目参考的三处

1. **分层记忆总体架构**：上下文窗口管短期、外部持久存储管长期、按需检索装载衔接——M4 检索层（ContextPack 组装注入）= "换入"的工程化，M5 工作层 = "主内存"概念；
2. **"记忆需要主动管理而非被动塞满"的判断**：把记忆管理变成显式机制，不赌模型自觉；
3. **核心记忆常驻 + 工作记忆轻载**：M1 规范层常驻事实库 + M4 按需检索（对应 MemGPT 核心记忆常驻 + 归档按需换入）。

### 33.3 与 MemGPT 的区别（对照表）

| 维度 | MemGPT | 本项目 |
|---|---|---|
| 记忆写入权 | 模型自己编辑（self-editing，写入无门控） | **模型只能"提议"，系统"裁决"**（候选隔离→证据校验→冲突检测→验收门控→策略裁决→转正） |
| 记忆单元 | 任意文本块 + 对话历史 | 结构化事实三元组（subject-predicate-value）+ 字节级证据锚定（span + sha256） |
| 检索方式 | embedding 向量检索（语义近似） | 结构化 SQL + FTS 关键词（精确匹配） |
| 遗忘机制 | 记忆压力触发模型自觉 evict | 验收巩固（什么进长期）+ supersedes 版本链（什么退出检索），确定性遗忘 |
| 可信度分层 | 无（写进去就是真的） | M0 候选/正式分层 + 冲突检测 + 策略裁决（decide_promotion） |
| 场景 | 通用对话 agent（单 agent 单对话） | 多智能体创作流水线（记忆服务创作一致性） |

### 33.4 最本质的区别：信任模型

- **MemGPT 信任模型**：记忆质量取决于模型自觉，写入无门控——存在幻觉记忆、记忆污染风险；
- **本项目信任系统**：模型只负责"提议"（抽取候选），系统负责"裁决"（证据校验、冲突检测、验收门控、策略裁决）——候选必须留在 M0、验收才转正、证据不可伪造。

### 33.5 一句话总结

**MemGPT 提供了"上下文当内存、存储当磁盘、按需换入换出"的分层记忆思想（架构灵感）；本项目把"模型自我编辑记忆"改为"模型提议 + 系统裁决"，把任意文本块改为带证据链的事实三元组，把向量语义检索改为精确结构化检索，并新增可信度分层与验收巩固——借鉴了它的"形"，替换了它的"魂"：从信任模型，变成信任系统。**

| 与 MemGPT 区别 | 写入权（模型自编 vs 提议+系统裁决）；事实三元组+证据 vs 文本块；精确检索 vs 向量语义；确定性遗忘 vs 模型自觉 evict |
